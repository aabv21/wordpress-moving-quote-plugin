# AGENTS.md

Guidance for anyone — human or AI — working in this repository.

## Purpose

This repo builds Chivabox Movers' moving-quote plugin: a WordPress plugin that gives instant moving estimates in a three-step form, saves every request in its own table, and delivers each lead to n8n as a signed request. In n8n the lead is recorded once, appended to a Google Sheet, and emailed to the team and the customer. It is a portfolio demo: every file should read as production-quality, not a prototype.

- `docker compose -f compose.yaml -f compose.queue.yaml down && docker compose up -d --wait` — return to the regular, single-process stack. Plain `down`, with no `-v`, keeps the named volumes.
- `npm run test:stack` — the full stack suite (`tests/stack/**`) against `vitest.stack.config.ts`: needs the whole stack (MySQL, WordPress, WP-CLI, Postgres, n8n) healthy and `./setup.sh` already run.
- `npm run test:stack:wp` — only `tests/stack/wp/`, the subset that needs just MySQL, WordPress, and WP-CLI. This is what CI's `stack` job runs on every PR.
- `npm run build:workflows` — bundles each `src/nodes/*.ts` Code node with esbuild into its node's `jsCode`, and sets its `notes` to `Why Code: <why>`. Add `-- --check` to fail (exit 1) if the committed JSON doesn't match the source, without writing — that's what CI runs.
- `npm run check` — hygiene checks on every file in `workflows/`: pinned data, `meta.instanceId`, required settings (including `errorWorkflow: cvbErrorHandler1` on every workflow except `error-handler` itself), a literal email/phone/long-id/secret, an unknown credential id, a hand-written or undocumented Code node, an external-service node without the required retry, a Postgres query built from an expression instead of `$n` parameters, a Postgres query with a `$n` placeholder inside a SQL comment, and a missing sticky note. `node scripts/check-workflows.ts <dir>` runs it against any directory and prints `<file>: <message>` per violation.
- `npm run setup` — imports credentials (`scripts/setup-credentials.ts`) and publishes workflows (`scripts/import-workflows.ts`) into the local n8n instance, in that order (`node scripts/setup.ts`, not `a && b`, so `-- --refresh <id>` reaches credentials too). Skips a credential whose `.env` values are blank, or one that already exists unless named with `--refresh <id>` (any number of times) — re-importing a credential replaces it, which would otherwise drop an interactive Google sign-in. Skips a workflow not yet in `workflows/`. After `import:workflow` exits 0, it verifies every manifest id actually landed with a read-only `n8n list:workflow --onlyId` and retries the import once on a miss, since a file freshly written right before the import can still be settling onto the bind mount when `import:workflow` reads the directory — failing clearly, naming the still-missing ids, if a retry doesn't recover them.
- `npm run export` — writes n8n's canonical form of every known workflow back to `workflows/` and regenerates their Code nodes; run this after editing a workflow in the n8n UI, and commit the result.
- n8n's `import:workflow`, `export:workflow`, `import:credentials`, `export:credentials`, and `publish:workflow` CLI commands need no owner account, `--userId`, or `--projectId` (checked against `2.45.6`). `publish:workflow` only takes effect after an n8n restart; `npm run setup` restarts n8n itself, but only when it actually published something, then waits for `/healthz` and an extra 15 s before polling each published workflow's webhook for 401 (see "Changing a workflow" below).

## The local stack

- **Services and ports.** `docker compose up -d --wait` brings up `db` (MySQL 8.4, unpublished), `wordpress` (on `127.0.0.1:8080`), `wpcli` (idle, for one-off `wp` commands), `cron` (runs `wp cron event run --due-now` every 60 s, since WP-Cron itself is disabled), `postgres` (unpublished), and `n8n` (on `127.0.0.1:5678`).
- **One stack at a time.** Every demo in this series binds `127.0.0.1:5678`, and this one also binds `127.0.0.1:8080`. Run `docker compose ls` first, and stop any other demo's stack before bringing this one up — otherwise `up` fails on the port conflict, or a test ends up talking to the wrong n8n.
- **`setup.sh`** requires `docker compose up -d --wait` to have already run. It waits for MySQL to actually accept TCP connections (its health status can turn healthy before the real server does), then installs WordPress (admin password read from `.env` over stdin, never as an argument), sets the site description, timezone, and pretty permalinks, activates the default theme and the `moving-quote` plugin, creates the `home`, `get-a-quote`, and `thank-you` pages, and sets the delivery settings: `webhook_url` to the in-network n8n address, and `webhook_secret`/`team_email` from `.env`'s `LEAD_WEBHOOK_SECRET`/`TEAM_EMAIL`, both piped through STDIN so neither touches the command line. It's idempotent: running it again touches nothing that's already correct.
- **Stack tests never use `wp db query`.** The `wpcli` image's bundled MariaDB client isn't guaranteed compatible with MySQL 8.4's wire protocol. `tests/stack/lib/stack.ts`'s `sqlWp()` instead runs `wp eval-file -`, which executes PHP through WordPress's own `$wpdb`, the same client the plugin itself uses at runtime.

## Changing a workflow

1. Design the nodes and expressions against n8n's own node reference and real-world examples.
2. Edit the JSON in `workflows/` (fixed IDs and credential IDs come from `scripts/lib/manifest.ts`), then run `npm run build:workflows` to regenerate any Code node it touches.
3. Validate the workflow JSON with an n8n-aware validation tool until it reports no errors. A Postgres node pinned at the real instance's current version can trip the validation tool's own stale `typeVersion` ceiling (see "n8n workflows" below) — that is the tool's data being behind, not a real error, and downgrading the node to silence it is wrong.
4. Run `npm run setup` to import and publish it against the local n8n instance.
5. Run `npm run export` to write n8n's canonical form back to `workflows/` and regenerate Code nodes again. Commit that exported output, not your hand-edited JSON — the two can differ in server-assigned detail, and the exported form is what actually runs.
6. Run `npm run setup` and `npm run export` a second time, then `git diff --exit-code workflows/` — a clean diff confirms import and export stay idempotent; a non-empty one means a field is leaking the instance's own state into the committed JSON (extend `scripts/lib/normalize-workflow.ts`'s volatile-fields list).
7. Run the full gate before committing.

A call made right after `npm run setup` restarts n8n can still run the previous published version for a few seconds: `/healthz` reports healthy well before the publication reconciler syncs `workflow_published_version` to the active version, which it does on its own schedule (10 s by default). `npm run setup` waits 15 s past `/healthz` for exactly this reason, then — for any manifest row that names a `webhookPath` — polls that workflow's webhook until it answers 401 (live and JWT-protected) before returning. After any other restart of the `n8n` container, wait the same 15 s before calling a workflow.

## Install lifecycle

- **Activate** (`Install\Installer::activate()`) creates the leads table through `dbDelta` (`Install\Schema::sql()`), seeds `moving_quote_settings` with the pricing defaults without overwriting an existing value, sets `moving_quote_db_version`, and schedules the outbox cron hook.
- **Deactivate** only clears the scheduled hook. The leads table and both options stay: deactivating is not the same as uninstalling.
- **Upgrade** (`Install\Installer::maybe_upgrade()`) runs on every `plugins_loaded`. When the stored `moving_quote_db_version` differs from the plugin's, it reruns `dbDelta` and updates the version, so an existing site picks up a schema change on its next request.
- **Uninstall** (`plugin/moving-quote/uninstall.php`, run only by WordPress when the plugin is deleted) drops the leads table, deletes both options, deletes the rate-limit transients, and clears the scheduled hook. This is the one path that removes data.
- **Cron.** Hook `moving_quote_process_outbox`, on the `moving_quote_every_minute` schedule (60 seconds), added through the `cron_schedules` filter. `Plugin::boot()` wires the hook itself to `Delivery\Outbox::process_due()`; see "Delivery" below.

## Settings

- **Admin page.** `Admin\Menu::register()` adds the "Moving quotes" top-level menu (capability `manage_options`, icon `dashicons-car`) and its Settings submenu, rendered by `Admin\SettingsPage::render()` as three sections: rates, cities and distances (existing routes, three blank rows, a remove checkbox, and a warning listing any missing city pair), and delivery.
- **Sanitizing a save.** `Admin\SettingsPage::sanitize()` applies a field-appropriate WordPress sanitizer — `esc_url_raw()` for the webhook URL, `trim()` only for the secret and the team email (never `sanitize_text_field()` or `sanitize_email()`, both of which can silently turn an invalid or tricky value into an empty string before the real validation ever sees it) — then hands the result to the pure `Settings\SettingsSanitizer`, which keeps a field's current value and reports an error code on any invalid input. `options.php` already unslashes the posted value, so this never unslashes a second time.
- **The webhook secret.** Submitting the form with the secret field left blank keeps the currently stored secret; only a non-blank value (at least 32 characters) replaces it. The rendered field is always `type="password"` with an empty value, so the page's HTML never contains the stored secret.
- **Delivery gating.** `Settings\Options::delivery_enabled()` is true only once the webhook URL, the webhook secret, and the team email are all non-empty; the settings page shows "Delivery is on" or "Delivery is off until the webhook URL, secret, and team email are set." accordingly.
- **`setup.sh`'s delivery keys.** It sets `webhook_url` to the in-network n8n address, and patches `webhook_secret`/`team_email` from `.env`'s `LEAD_WEBHOOK_SECRET`/`TEAM_EMAIL` through `wp option patch update …`, both piped over STDIN.

## Leads admin

- **The page.** `Admin\Menu::register()` points the top-level "Moving quotes" page and its "Leads" submenu at `Admin\LeadsPage::render()`, which requires `wp-admin/includes/class-wp-list-table.php` (not autoloaded by core) before instantiating `Admin\LeadsListTable`, a `WP_List_Table` subclass. Columns: Received (`America/Bogota`), Reference, Customer (name, phone, email), Move (date, type, rooms), Route (origin → destination, km), Estimate (the same `COP low – high` display text the REST API uses), Status (a per-row form posting to `admin-post.php`), and Delivery (the sync label, attempt count, `last_error` in a `title`, and a "Retry delivery" link on `failed` rows only). Views: All and the five `LeadStatus` values, each with a live `COUNT(*)`-backed count; 20 rows per page; an unrecognized `status` query arg reads as "All".
  - `LeadsListTable::single_row_columns()` overrides the base class's generic column dispatch to call this table's own `column_$name()` methods directly, each already escaping its own dynamic output (`esc_html`/`esc_attr`/`esc_url`); it must not run that trusted markup back through `wp_kses_post()`, which would strip the status column's own `<form>`, `<select>`, and hidden `<input>` tags (none of which are in `wp_kses_post()`'s post-content allow-list).
- **The handlers.** `Admin\LeadsPage::register_hooks()` wires three `admin_post_moving_quote_*` actions. `admin-post.php` itself has no capability gate (unlike a menu page, which core's own `wp-admin/includes/menu.php` already denies with 403 before any callback runs) — every handler here calls `current_user_can( 'manage_options' )` itself first, `wp_die()`-ing with an explicit `403` (`wp_die()` defaults to 500 otherwise) before it ever calls `check_admin_referer()`.
  - `handle_update_status()` reads the posted `status`, applies it through `LeadRepository::update_status()` (an unrecognized value is a no-op), and redirects to the list with a notice.
  - `handle_retry()` calls `LeadRepository::requeue()`, which only acts on a `failed` row: back to `pending`, attempts reset to 0, due immediately. The redirect notice says the lead was "queued for delivery" — never "sent", since this only requeues it; actual delivery is cron's job.
  - `handle_export()` sends `nocache_headers()`, `text/csv; charset=utf-8`, and `attachment; filename="moving-leads-{Y-m-d in Bogota}.csv"`, writes the UTF-8 BOM and the `Admin\LeadCsv::HEADER` row, then streams `LeadRepository::chunk_after()` batches of 500 (an ascending-id cursor, so a row added mid-export can't be skipped or re-read the way `page()`'s `created_at` ordering could) through `fputcsv( $out, $row, ',', '"', '' )` — note its default row terminator is a plain `\n`, not `\r\n` — and `exit`s right after, so nothing can `echo` onto the stream afterward.
- **CSV safety.** `Admin\CsvEscaper::cell()` (pure) prefixes a value with `'` when its string form starts with `=`, `+`, `-`, `@`, a tab, or a carriage return — the set of prefixes that make Excel, LibreOffice, or Google Sheets read a cell as a formula — so hostile data already in the table (e.g. a name typed as a formula) can never execute when the export is opened; `null` becomes `''`. `Admin\LeadCsv::row()` (pure) builds one row from a `LeadRecord`: `received_at` converts `created_at` (stored UTC) to the given timezone and formats `Y-m-d H:i`; every other field (`status`, `move_type`, the comma-joined `extras`, `sync_status`, …) is the raw stored value, not its display label; every cell passes through `CsvEscaper`.
- **The stuck-delivery notice.** `Admin\StuckDeliveryNotice::register()` hooks `admin_notices`; `maybe_render()` shows a `notice-warning` only to a `manage_options` user on the Dashboard (`get_current_screen()->id === 'dashboard'`) or the Leads page (`'toplevel_page_' . Menu::SLUG`), and only when `LeadRepository::count_stuck()` (every `failed` lead, plus every `pending` lead whose `created_at` is over an hour old) is non-zero. The notice text states the count and links to the Leads page.

## REST API

- **`POST /wp-json/moving-quote/v1/estimate`** (`Rest\EstimateController`). No nonce. Rate limit: `estimate` bucket, 120 per 600 s. Validates and prices with `Leads\LeadValidator::quote()` and `Pricing\Calculator`, against the current settings. Responses: 200 with the estimate; 422 `moving_quote_invalid` (`data.errors`, field to message); 429 `moving_quote_rate_limited` with a `Retry-After` header.
- **`POST /wp-json/moving-quote/v1/leads`** (`Rest\LeadController`). Requires `X-WP-Nonce` (action `wp_rest`). In order: nonce check, honeypot (`website`), validation (`Leads\LeadValidator::lead()`), pricing, a duplicate lookup by `submission_id` (= `request_uuid`), the `submit` rate limit, then the insert.
  - **The `submit` rate limit (5 per 3,600 s) is counted only once a lead is about to be inserted** — after the honeypot, validation, and the duplicate lookup all pass. A customer correcting a typo, or double-tapping Submit, never burns through the limit on an attempt that was never going to save anything; only a genuinely new lead counts.
  - **Both routes register with no `args` schema.** A restrictive schema would make core answer its own 400 `rest_invalid_param` before the route runs, preempting the 422 contract. Every field is validated by `LeadValidator` instead.
  - **The nonce has two error codes.** A missing `X-WP-Nonce` header gets the plugin's own 403 `moving_quote_bad_nonce`. A stale or forged nonce never reaches the plugin at all: WordPress core's `rest_cookie_check_errors` rejects it first, with 403 `rest_cookie_invalid_nonce` ("Cookie check failed"). The estimate route sends no nonce and must never receive one from the frontend.
  - Responses: 201 `{"ok":true,"reference":"MQ-…","estimate":{…}}` for a new lead; 200 with the same shape for a duplicate `submission_id` (nothing is saved or counted against the limit again); 201 `{"ok":true}` for a filled honeypot (nothing saved); 422 `moving_quote_invalid`; 429 `moving_quote_rate_limited`; 500 `moving_quote_save_failed` for any other insert failure (logged without PII).
- **`Security\RateLimiter`** stores fixed-window counts in transients keyed `moving_quote_rl_{bucket}_{hash}`, hashed from the client IP so the IP itself never appears in the database. `client_ip()` reads `REMOTE_ADDR`, filterable through `moving_quote_client_ip`.

## Delivery

Every saved lead is sent to n8n as a signed, authenticated HTTP request: once right after the insert, and from then on through a cron-driven outbox that retries a failed attempt with backoff.

- **Signing and payload.** `Delivery\JwtSigner::hs256()` signs a claims array into a compact HS256 JWT (base64url without padding). `Delivery\LeadPayload::body()` builds the exact JSON contract body (`JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE | JSON_THROW_ON_ERROR`, `submitted_at` as `created_at` converted to `America/Bogota` and formatted with `DATE_ATOM`); `tests/fixtures/lead-payload.json` holds that exact body for one fixed lead, shared between `tests/php/Delivery/LeadPayloadTest.php` and the global contract documentation. `LeadPayload::claims()` derives the JWT claims (`jti` = `request_uuid`, `iat`, `exp` = `iat + 300`, `body_sha256`) from the already-built body, so the signature binds to the exact bytes sent.
- **Response checks and retries.** `Delivery\ResponseCheck::acknowledged()` is the one place that decides whether n8n's response counts as delivered: a 2xx whose JSON `status` is `accepted` or `duplicate`. `Delivery\Backoff::delay_after()` is the retry schedule: `min(60 × 2^(n-1), 21600)` seconds after the n-th failure, giving up after `MAX_ATTEMPTS` (10). `Delivery\SyncTransition::after_attempt()` turns one attempt's outcome into a `Delivery\SyncUpdate` (the next `sync_status`, attempt count, `next_attempt_at`, `last_error` cut to 500 characters with `mb_substr`, and `sent_at`), with no WordPress or database dependency — every case in the backoff and status-transition table is covered by an exact PHPUnit case, not a range check.
- **`Delivery\WebhookClient::send()`** is the one place that calls `wp_remote_post()` (not `wp_safe_remote_post()`: the admin sets the URL themselves, and it is a private Docker hostname the safe variant's SSRF guard would otherwise block), with a 5 s timeout and no redirects. It returns null on an acknowledged 2xx, otherwise the error text: a `WP_Error`'s message, `HTTP {code}: {excerpt}` for a non-2xx, or `Unexpected response (HTTP {code}): {excerpt}` for an unacknowledged 2xx.
- **`Delivery\Outbox`** ties it together. Delivery is at-least-once, not exactly-once: n8n dedupes on `jti` (= `request_uuid`), and `apply_sync()`'s `pending` guard keeps an already-`sent` row `sent`. `deliver( LeadRecord $lead )` builds the payload body, the JWT claims, and the signed JWT itself, sends the request, and stores the resulting `SyncUpdate` through `LeadRepository::apply_sync()` — it does not claim the row itself. `process_due()` is the cron entry point and the one caller that does claim: it returns 0 without querying when `Options::delivery_enabled()` is false, otherwise it loads up to `BATCH_SIZE` (20) due rows through `LeadRepository::due()`, calls `LeadRepository::claim()` on each one with a lease counted from the moment of that call (not from when the batch started, so a slow batch never claims a later row with an already-stale lease), and calls `deliver()` only on the rows it actually claims. `LeadController`'s inline attempt (below) calls `deliver()` directly with no claim of its own, since `insert()` already set that row's `next_attempt_at = now + LEASE_SECONDS`, so no cron run can see it as due until that lease expires. A row whose `status` column `LeadRecord::from_row()` can't parse (`LeadStatus::from()` throwing `ValueError`, most likely written by a different plugin version) is recorded as a failed attempt using its own stored `attempts` and skipped, instead of losing the rest of the batch behind it.
  - **Every internal failure still counts as an attempt.** A `Throwable` caught anywhere in the delivery path goes through the same `SyncTransition::after_attempt()` call a genuine HTTP failure would, with `last_error` `Internal error: {class}` — never the exception's message, which could carry PII pulled from the lead. This is what makes a persistent internal fault back off and eventually reach `failed` instead of retrying every lease window forever, and it is never logged separately.
  - **Two lifecycle writes are guarded against a stale worker.** `LeadRepository::claim( $id, $expected_next_attempt_at, $lease_until )` is an `UPDATE` matched on `id`, the row's current `next_attempt_at`, and `sync_status = 'pending'`; it returns true only when exactly one row changed. `LeadRepository::apply_sync()` writes only while `sync_status = 'pending'`, so a worker holding a stale lease can never overwrite a row a faster, overlapping run already marked `sent`.
    - NOTE: a runner stalled past its own lease can still be overtaken by a second runner, which claims and delivers the row; if that second runner then fails and the row goes back to `pending`, the first runner's own late write can still land and mask the second runner's outcome, since `apply_sync()` only checks `sync_status`, not which lease issued the write. Fencing `apply_sync()` on the lease value `claim()` issued, not just on `sync_status = 'pending'`, would close that gap.
  - **`LeadController`'s inline attempt** runs `Outbox::deliver()` inside a try/catch, only after a *new* insert (never for a duplicate `submission_id` that found an existing row) and only when `Options::delivery_enabled()`. The response is 201 regardless of the delivery outcome, so the customer never sees an error the outbox's own retries will resolve on their own; this can still delay that 201 by up to `WebhookClient`'s 5 s timeout.
- **Stack-test helpers.** `tests/stack/lib/receiver.ts`'s `startReceiver()` is a tiny HTTP server standing in for n8n's webhook, listening on `0.0.0.0` on an ephemeral port at `http://host.docker.internal:<port>/lead` (every container in `compose.yaml` declares that host through `extra_hosts`, so it's reachable from WordPress, wpcli, and the cron sidecar, on Linux CI too). `tests/stack/lib/jwt.ts`'s `signHs256()` and `decodeVerified()` sign and verify an HS256 JWT with `node:crypto`; `decodeVerified()` uses a constant-time signature comparison and is asserted with `not.toBeNull()`, never by comparing a secret. `tests/stack/lib/leads.ts` tracks every `request_uuid` a test mints through `validLead()` and exposes `deleteCreatedLeads()` to sweep them: a saved lead is a real delivery attempt, and cron keeps retrying a pending one for hours, so every stack file that creates leads calls `deleteCreatedLeads()` in `afterAll`. `tests/stack/lib/stack.ts`'s `disableDelivery()` patches `webhook_url` to `''` and returns a restore function, for a file whose leads must never actually reach the configured n8n URL.
- **Keeping `tests/stack/wp/delivery.test.ts` deterministic.** `tests/stack/global-setup.ts` already stops the `cron` sidecar for the whole stack-test run (restarting it afterward only if it was running), so its background `wp cron event run --due-now` loop doesn't race this file's assertions in practice. The file still parks every other pending row (`next_attempt_at` far in the future) before each case and again afterward, and filters the receiver's recorded requests by the body's `request_uuid` rather than assuming "the last request" is its own, as a second layer of defense: both are cheap, and they keep the file correct even if that sidecar is ever running during a manual or partial run.

## n8n workflows

`workflows/lead-intake.json` (published as `cvbLeadIntake001`) is the WordPress-to-n8n handoff's receiving end. Every node in order:

1. **Receive lead** (Webhook v2.2). `POST moving-quote/leads`, `authentication: jwtAuth` against the `Lead webhook JWT` credential (`cvbCredLeadJwt01`), `responseMode: responseNode` (a later Respond to Webhook node answers the caller), `options.rawBody: true` (the exact bytes land in binary `data`, for the next node to hash). The native JWT check reads `Authorization`, verifies the signature with `jsonwebtoken`, and verifies `exp` only when it's present (`jsonwebtoken.verify` skips that check on a token with no `exp` claim at all), rejecting a missing token (plain-text 401) or a bad signature, an expired token, or `alg: "none"` (plain-text 403) before any execution starts — so none of those four ever reaches Postgres or shows up as a workflow error. A signed token with no `exp` passes this check and reaches **Verify request** below, which rejects it as `missing_claims`.
2. **Hash raw body** (Crypto v2). `action: hash`, hashing the binary `data` field into `body_sha256` as lowercase hex SHA-256 — the same bytes, the same algorithm, as `Delivery\LeadPayload::claims()`'s `body_sha256` claim, so the two can be compared exactly.
3. **Verify request** (Code, generated from `src/nodes/verify-request.ts`). The native check above verifies the signature, and `exp` only when it's present, but not that `exp` is an integer, how long the token lives, or that it's bound to this exact body — one tested function checks all of that, the payload contract, and the `jti`/`request_uuid` binding, instead of a chain of IF nodes. In order: the four claims are present with the right types (`missing_claims`); the lifetime is at most 300 s (`token_lifetime`); `iat` is at most 60 s in the future (`token_not_yet_valid`); `exp` hasn't passed (`token_expired`); `body_sha256` matches the computed hash (`body_hash_mismatch`); the body parses against the contract (422 `invalid_payload`); `jti` equals the parsed `request_uuid` (`jti_mismatch`). `src/nodes/lead.ts`'s `parseLead()` checks `move.date` only as a valid calendar date — the today-through-365-days window is WordPress's own submit rule (`Leads\LeadValidator`), and re-enforcing it here would reject a lead whose window has since closed on a legitimate retry, or a same-day retry made after midnight, forever.
4. **Request valid?** (IF). Tests `{{ $json.ok }}` (a boolean-true comparison on `Verify request`'s own output). True goes to **Read config**; false goes to **Reject request** (Respond to Webhook, JSON `{ status: 'rejected', reason }`, HTTP code from `{{ $json.status }}` — the 401/422 `Verify request` itself returned, not the response body's own `status` field).
5. **Read config** → **Parse config**. Reads `/files/config/config.json` (Read/Write Files from Disk) and extracts it into `config` (Extract From File, `fromJson`). A `fileSelector` that matches nothing makes Read/Write Files v1.1 throw its own `No file(s)…` error directly (verified against the real instance's stored error runs), failing the whole execution before **Record request** ever runs — n8n answers its own 5xx, loudly, rather than an empty 200 nobody notices. `alwaysOutputData: true` and `executeOnce: true` are still pinned on **Read config** as defense in depth, in case a future n8n version changes that node's empty-match behavior to return zero items instead of throwing.
6. **Record request** (Postgres v2.8, credential `App DB` / `cvbCredAppDb0001`, retry 3× at 1000 ms). `INSERT INTO processed_events (source, event_id) VALUES ('wordpress-lead', $1) ON CONFLICT DO NOTHING RETURNING event_id`, with `$1` bound through `options.queryReplacement` to `{{ $('Verify request').first().json.lead.request_uuid }}`. The Postgres node itself (v2.3+) synthesizes a `{ success: true }` item with no `event_id` when `RETURNING` matches no row (a replay) — `alwaysOutputData: true` is pinned so that synthesized item still reaches the gate after it, not because it causes the synthesis.
7. **New request?** (IF). Tests that `{{ $json.event_id }}` exists (a string-exists comparison), not a row count: `ON CONFLICT DO NOTHING RETURNING event_id` already gives exactly one `event_id` for a genuinely new id and none for a replay, so testing existence is the direct read of that mechanism, not an inference from it. True goes to **Respond accepted** (200 `{"status":"accepted"}`); false goes to **Respond duplicate** (200 `{"status":"duplicate"}`) — both are what `Delivery\ResponseCheck::acknowledged()` treats as delivered.
8. **Prepare lead** (Edit Fields, manual mode) → **Process lead** (Execute Workflow), after **Respond accepted** only — never after **Respond duplicate**, since a replay's lead was already processed on its first delivery. **Prepare lead** builds `{ lead, config }` from `$('Verify request').first().json.lead` and `$('Parse config').first().json.config`; **Process lead** calls `cvbProcessLead01` by ID (`mode: 'each'`, `options.waitForSubWorkflow: false`), fire-and-forget. See "process-lead" below for the business side this hands off to.

**Why Postgres is pinned at 2.8, and the MCP false positive.** n8n 2.45.6 genuinely offers Postgres node v2.8 (confirmed by publishing this workflow against the real local instance and exporting it back unchanged). The n8n-mcp tool's own bundled node database is slightly behind that: `validate_workflow` reports `typeVersion 2.8 exceeds maximum supported version 2.7` on this workflow, which is that tool's own data being stale, not a real problem — do not "fix" it by downgrading the node. `tests/workflows.test.ts` pins every Postgres node across `workflows/` at 2.8 for exactly this reason: a downgrade would pass the MCP's validator and silently drop a version the real instance already runs fine.

**Anchoring expressions.** Every reference to another node's output in every workflow here uses `.first()` (e.g. `$('Verify request').first().json.lead.request_uuid`), never `.item` — `.item` depends on how n8n pairs a Code node's output item with its caller's, which isn't guaranteed the way a direct index is. NOTE: one webhook call carries exactly one lead, so `.first()` is always the whole, correct answer here; a workflow that ever batched several leads through one execution would need a different anchor. `process-lead`'s own nodes anchor the same way, including its reference back to the parent's own input (`$('When called').first().json.lead...`).

### process-lead

`workflows/process-lead.json` (published as `cvbProcessLead01`) is the business side: Google Sheets and the two notification emails, entered only through `lead-intake`'s fire-and-forget hand-off above, never directly. Input contract: `{ lead, config }`. Every node in order:

1. **When called** (Execute Workflow Trigger). `inputSource: 'passthrough'`, so it accepts exactly the shape its one caller sends with no declared schema to drift out of sync.
2. **Map lead** (Code, generated from `src/nodes/map-lead.ts`). One tested function builds the sheet row and both notification emails from the lead in one pass, instead of a Set node and several expression-filled Gmail/Sheets fields each doing their own formatting:
   - `row`: the sheet row, keys in `SHEET_HEADERS` order. `received_at` is `submitted_at` converted to `America/Bogota` and formatted `yyyy-LL-dd HH:mm`; `move_type` and `extras` use their English labels (`extras` joined with `, `); every other field, including `phone` and a formula-looking `name`, passes through unchanged as text or stays a number — nothing here reformats a value the way a spreadsheet's own type coercion might.
   - `team`: `{ to, subject, text }`, the plain-text team alert (see "Why Email team is plain text" below).
   - `customer`: `{ to, reply_to, subject, html }`, the escaped-HTML customer summary. `escapeHtml()` covers `& < > " '`, so a crafted customer name can never break out of the `<p>` tags it's interpolated into.
3. **Row fields** (Edit Fields, JSON mode). `jsonOutput: '={{ $json.row }}'` — the row Google Sheets will auto-map by field name.
4. **Append lead row** (Google Sheets, credential `cvbCredGSheets01`, retry 3× at 1000 ms). `operation: 'append'`, `documentId`/`sheetName` resource locators read from `$('When called').first().json.config.google.leads_sheet_id`/`leads_tab` (`sheetName` in `name` mode: Sheets only matches a tab by title, not a numeric id, in that mode), `columns.mappingMode: 'autoMapInputData'`, `options.cellFormat: 'RAW'` — the pin that makes the phone column store `570000000001` as literal text instead of `5.7E+11`, and a formula-looking name store as literal text instead of running.
5. **Email team** and **Email customer** (Gmail, credential `cvbCredGmail0001`, retry 3× at 1000 ms, both wired from **Append lead row** so a lead that never reached the sheet still notifies no one), both reading from **Map lead**'s own output:
   - **Email team**: `emailType: 'text'`, every field from `$('Map lead').first().json.team`.
   - **Email customer**: `emailType: 'html'`, every field from `$('Map lead').first().json.customer`, plus `options.replyTo` set to `customer.reply_to` (the team's address) so a reply from the customer reaches the team, not n8n.
   - Both set `options.appendAttribution: false` (no "This workflow was built with n8n" footer) and `options.senderName` from `$('Map lead').first().json.sender_name` — `site_name` normalized by the same `oneLine()` the sheet row and team body already use, shared by both nodes so neither carries its own, separately-escaped copy.

**The cost of appending before emailing.** Wiring both Gmail nodes from **Append lead row** means a lead that fails there sends no email at all until someone retries the execution — and WordPress has already marked that lead `sent`, since `lead-intake` answered `accepted` before any of this ran. The operator alert from `error-handler` is the only signal that happened. That alert uses the same Google OAuth client as **Append lead row** and both Gmail nodes, so a grant that's expired (Testing mode's own OAuth consent screen caps a refresh token at 7 days) silences the sheet append, both emails, and the alert about all three in the same stroke.

**The email rule, agreed on both sides.** `LeadValidator::validate_email()` (WordPress) and `parseCustomer()`/`team_email`'s check (`src/nodes/lead.ts`) now reject the same shape: after `FILTER_VALIDATE_EMAIL` passes, both also reject any address containing whitespace, a control character, or any of `" , ; < > ( ) [ ] : \`. That closes the one gap `FILTER_VALIDATE_EMAIL` alone leaves open — a quoted local part such as `"a,b"@example.com`, which Gmail's own `sendTo` splits on the comma into a second recipient, so one submission could otherwise address the estimate email to several people. `?`, `&`, and `=` are deliberately still allowed in the local part: a crafted lead can still set an email whose "local part" is actually `victim@example.com?body=...` and get a `mailto:` link that pre-fills a reply to someone else, which is exactly why Email team stays plain text, with no `tel:`/`mailto:` links, rather than HTML. Plain text has no links to craft in the first place; Gmail's own rendering still turns a recognizable phone number or email address in plain text into a tappable link on its own, so nothing is lost for a genuine lead. The customer email stays HTML (richer formatting for the estimate and disclaimer matters more there, and it's addressed to the lead's own, already-exposed email — the attack surface plain text closes is specifically the *team* alert, built from the same untrusted fields).

**Line-break injection, on both sides.** A plain-text email has no markup to escape, only lines — so a control character in a lead field could otherwise forge an extra "Phone:"/"Email:"/etc. line in the team alert. `LeadController` passes the raw REST body straight to `LeadValidator`, with no `sanitize_text_field()` pass first, so the real guarantee is `LeadValidator::validate_name()`: it normalizes every C0 control, DEL, NEL (U+0085), LINE SEPARATOR (U+2028), and PARAGRAPH SEPARATOR (U+2029) to a single space before `parseLead()` ever sees `customer.name`, `move.origin`, or `move.destination` — which still reject that exact set outright, as a second check against anything that skipped WordPress. `map-lead.ts`'s `oneLine()` runs every lead-derived value interpolated into `team.text`'s body through the same set, so the team email stays one line per field even if a future caller ever bypassed both. `site_name` and `team_email` are deliberately left out of the `parseLead` check: neither ever lands in a multi-line body (`site_name` only reaches `sender_name` and an already-`oneLine()`'d subject; `team_email` only reaches a `to`/`reply_to` field, never body text).

### error-handler

`workflows/error-handler.json` (published as `cvbErrorHandler1`) is the shared workflow every other workflow's `settings.errorWorkflow` points to. It reads config itself, through its own nodes — never through a sub-workflow (unlike demo 3's `error-handler`, which calls a dedicated `load-config` workflow) — because a sub-workflow call here would need its own `errorWorkflow`, and naming this same handler would start a second alert for the first alert's own failure; naming none means a missing or unparseable `config/config.json` fails this handler once and stops, with no loop. Every node in order:

1. **On workflow error** (Error Trigger). Fires on any workflow whose `settings.errorWorkflow` is `cvbErrorHandler1`, including a trigger or activation failure (e.g. a revoked credential at startup), which carries no `execution` key at all — only `trigger`.
2. **Read config** → **Parse config**, identical to `lead-intake`'s own pair (`/files/config/config.json`, `alwaysOutputData: true` and `executeOnce: true` pinned on **Read config** as the same defense in depth).
3. **Email operator** (Gmail, credential `cvbCredGmail0001`, retry 3× at 1000 ms, `emailType: 'text'`). Sent to `config.alerts.error_email` — not `$json.workflow.name`-shaped data, since `$json` here is `{ config }` after **Parse config**, not the trigger's own output. Every field instead anchors on `$('On workflow error').first().json`, with an inline destructuring-arrow IIFE and optional chaining (matching demo 3's own `error-handler.json` form):
   - Subject: `[Chivabox demo] Workflow failed: {{ workflow?.name ?? 'unknown workflow' }}`.
   - Body: the failing node (`execution?.lastNodeExecuted ?? 'activation'`), the error message (`execution?.error?.message ?? trigger?.error?.message ?? 'unknown error'`), the execution URL (`execution?.url ?? 'n/a (activation error)'`), and the time in Bogota (`$now`, which needs no anchor — it's a global, not another node's output).

Every one of those four expressions was resolved through n8n's real data proxy on its `vm` expression engine, for both an execution-error and a trigger-error payload, with every fallback firing exactly where `execution` is absent.

### Two answers about publishing and versions

- **Does n8n 2.45.6 publish a workflow whose Google credentials don't exist yet?** Yes. `process-lead.json` references `cvbCredGSheets01` and `cvbCredGmail0001` throughout, and neither credential existed in this instance (confirmed with a non-decrypted `export:credentials` listing both missing) when `import:workflow` and `publish:workflow --id=cvbProcessLead01` both ran clean, with the workflow coming up `active: true`. Credential existence is checked only at execution time — "Append lead row" fails there with `Credential with ID "cvbCredGSheets01" does not exist for type "googleSheetsOAuth2Api."` — never at import or publish time.
- **Which version does a webhook-started parent call: the sub-workflow's published version, or its latest?** The published (active) version, for every workflow in the chain, parent or sub-workflow — true for a production run (a live trigger, or retrying a past execution) in every case checked here. Verified by publishing `cvbProcessLead01` at a named, older `--versionId` (via n8n's `publish:workflow --id=... --versionId=...`) while importing a newer, unpublished draft version of the same file, then sending a real signed lead through the live webhook: the resulting `process-lead` execution's own `execution_entity.workflowVersionId` column recorded the older, *published* version id, not the newer draft's — even though the draft was n8n's own "current version" at the time of the call. The same held for the webhook-started `lead-intake` execution itself. A manual or chat-triggered run is a separate case this repo never runs in production and hasn't checked: n8n's own `isManualOrChatExecution` branch (`workflow-execute-additional-data.js`) loads the workflow's *draft* data for exactly that execution mode, so a manual "Execute Workflow" click in the editor is expected to run whatever is unpublished, not what this note covers.

### The false-duplicate failure mode

`lead-intake`'s **Record request** retries 3 times on failure (see the node list above), which is correct for a genuine transient error — but it means an `INSERT ... RETURNING event_id` that actually committed, whose acknowledgement was then lost before n8n saw it (a dropped connection, Postgres restarting mid-response), gets retried as the *same* statement. The retry's `ON CONFLICT DO NOTHING` finds the row already there and returns no `event_id`, so **New request?** reads it as a replay: `Respond duplicate` goes back to WordPress, and — because the hand-off to `process-lead` is wired only from `Respond accepted`, never from `Respond duplicate` — that lead's row, email, and sheet append never run, even though it was genuinely new.

The retry stays: losing it would make a real transient failure permanently drop a lead instead of recovering from one, which is the far more common case. The symptom and recovery:

1. **Symptom.** A lead is present in `processed_events` (so `lead-intake` itself saw it as accepted or duplicate) but missing from the `Moving leads` sheet — found by comparing a WordPress lead's `request_uuid` against both tables, not by anything n8n itself flags.
2. Delete that lead's row from `processed_events` (identified by its `event_id` = the lead's `request_uuid`).
3. Set the matching WordPress leads-table row's `sync_status` back to `pending` and its `next_attempt_at` due (0, or any time in the past).
4. Run the outbox cron (`wp cron event run moving_quote_process_outbox`, or wait for the sidecar's own 60 s loop). WordPress's own retry resends the identical signed lead; with the `processed_events` row gone, this time it's a genuinely new id, so it reaches `Respond accepted` and the hand-off to `process-lead` runs.

**Security: what n8n 2.45.6 actually does with the stored token.** It stores the incoming `Authorization` header verbatim in `execution_data` for every outcome of this workflow, with no redaction — confirmed from `ExecutionPersistence.create()`, which builds the trigger output from raw `req.headers`. What happens to that row next depends on how the run ends:
- **Accepted, duplicate, and 401/422-rejected runs all succeed at the workflow level.** With `saveDataSuccessExecution: 'none'`, the save hook soft-deletes the row instead of keeping it: with pruning on (`EXECUTIONS_DATA_PRUNE: true` in `compose.yaml`), that sets `deletedAt` to roughly one hour in the past (n8n's hard-delete buffer), while `status` itself stays `running` — `deleteInFlightExecution()` returns before writing a terminal status, in any response mode, so this holds for `process-lead`'s own successful runs too once Google is wired in. n8n's hard-delete task (every 15 min by default) then purges every row whose `deletedAt` has passed, taking `execution_data` with it through the FK cascade. **So a successful run's token is gone at the next hard-delete cycle — up to about 15 minutes, longer if n8n restarts often, since each restart resets that task's own timer** — not kept until `EXECUTIONS_DATA_MAX_AGE`.
- **A genuinely failed run** (the missing-`config.json` case, not a 401/422 rejection) keeps its full data, including the token and the customer's name, phone, and email, until `EXECUTIONS_DATA_MAX_AGE` (168 hours here) — `settings.saveDataErrorExecution` is left at its default for exactly this: a failed run needs its data for diagnosis. The same token-lifetime and body-binding limits below apply to it too, so a saved failure's token carries no more risk than a saved success's before its own soft-delete.
- **A manual run** (started from the editor's "Execute Workflow" button) is soft-deleted under `saveManualExecutions: false` without the backdate, so it's purged an hour or more later than a production run.

`tests/stack/n8n/intake.test.ts`'s cases on this read only n8n's own tables (finding an execution by its `request_uuid`, never by a token) and never write to them — the soft-delete and the eventual hard-delete are n8n's own job, on n8n's own schedule.
What actually bounds the risk in the meantime: the token's own lifetime is at most 300 s past `iat` (`verify-request`'s own `token_lifetime`/`token_expired` checks, enforced independently of whatever n8n stores), it's bound to one exact body by `body_sha256`, and its `jti` is the lead's own `request_uuid`, which `processed_events`' `(source, event_id)` primary key dedupes — so a token read out of a stored execution, even before it's purged, can replay the same lead but can never create a second one. There is no execution-level redaction in n8n 2.45.6 that removes this exposure for a `responseNode` webhook; the mitigation here is that a leaked token's blast radius and its window are both bounded, not that the token is hidden.

**Keeping test leads away from live Google.** Every stack-test case that reaches `process-lead` skips itself, with a console message naming why, once `tests/stack/lib/stack.ts`'s `googleCredentialsConfigured()` finds either Google credential (`scripts/lib/manifest.ts`'s `googleCredentialIds(CREDENTIALS)`, never a hand-maintained id list) already in n8n — checked the same way `scripts/setup-credentials.ts` checks it, from a non-decrypted `export:credentials` listing of IDs, never a decrypted one. `tests/stack/n8n/end-to-end.test.ts` and `tests/stack/n8n/process-lead.test.ts` skip their entire `describe` block this way; `tests/stack/n8n/intake.test.ts` marks only its own accepted-lead cases with `it.skipIf(...)`, since its rejection cases and its missing-config case never reach `process-lead` at all. Without this guard, running the local suite after the owner wires in the real Google account would append a test row to the real `Moving leads` sheet and email the real team on every run.

## The quote form

- **Shortcode.** `[moving_quote]` (`Frontend\Shortcode::TAG`), with one optional attribute, `thank_you` (the slug of the page to redirect to on success; defaults to `thank-you`). `Shortcode::register_assets()` registers the script (footer, `strategy: 'defer'`) and style on `init`; `Shortcode::render()` enqueues both, so they load only on a page that actually uses the shortcode.
- **Markup** (`templates/quote-form.php`). A `<form data-moving-quote data-config="…">` with three `<fieldset>`s (move details, extras, customer details), a progress `<ol>`, a honeypot (`name="website"`, visually and from Tab order, but still present for a screen reader and for any bot that fills every field by DOM access instead of tabbing), and a `<noscript>` fallback. Move type, rooms (1–5, "5+"), and both city selects are rendered server-side from `Pricing\MoveType` and `DistanceTable::cities()`; each city select starts with a disabled "Choose a city" placeholder. `data-config` is `wp_json_encode()` run through `esc_attr()`, so a city name or any other merchant-editable string can never break out of the attribute.
- **Frontend** (`src/frontend/quote-form.ts`, plus `src/frontend/lib/{debounce,latest,uuid,api,form-state}.ts`, each independently unit-tested). One `submission_id` (a browser-minted UUID v4) per page load, reused on every retry. The estimate call runs through `debounce(latestOnly(...), 300)`: a burst of edits collapses to one request 300 ms after the last one, and a response for input that's since been superseded is discarded instead of overwriting a newer result. Moving between steps shifts focus to the new step's `<legend>`. Submitting disables the button and shows "Sending…"; a 2xx redirects to the thank-you page (or shows an inline success message when that page doesn't exist); a 422 shows the field errors and jumps back to the first step with one; a 403 (either `moving_quote_bad_nonce` or core's `rest_cookie_invalid_nonce`), a 429, or a network failure shows the matching message and re-enables the button. No path shows success, or leaves the button disabled, on anything but a genuine 2xx.
- **The generated asset.** `plugin/moving-quote/assets/quote-form.js` is built by `npm run build:assets` (`scripts/build-assets.ts`, esbuild) and committed; CI fails the build if it drifts from the source (`build:assets -- --check`). Never edit it by hand — change `src/frontend/**` and rebuild.

## Conventions

- Node 24 (`"engines": { "node": ">=24" }`), ESM (`"type": "module"`). `tsconfig.json` runs `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, `allowImportingTsExtensions`, with `noEmit` — there is no build step.
- No `.js` or `.mjs` source files. Scripts are `scripts/*.ts`, run directly with `node scripts/<name>.ts` (Node's native type stripping; no `tsx`). Tests are Vitest files at `tests/**/*.test.ts`. The only JavaScript in the repo is generated: the compiled frontend asset (`plugin/moving-quote/assets/quote-form.js`) and each Code node's `jsCode`.
- A test outside `tests/stack/` never imports `tests/stack/lib/stack.ts`, or anything that imports it: that module calls `process.loadEnvFile('.env')` at import time, and CI's Quality job (`npm test`) has no `.env` — only the stack job runs `init-env.ts` first. A helper two or more stack-test files need, with no dependency on the live stack itself, belongs in its own side-effect-free module instead (e.g. `tests/stack/lib/poll.ts`), so a unit test can import it directly without pulling in `stack.ts`.
- CLIs call external programs with `execFile` or `spawn` and an argument array, never a shell string, and guard their entry point so tests can import their functions without side effects.
- Comments only where intent isn't obvious. A deliberate simplification gets one `NOTE:` line naming its ceiling and upgrade path.
- Local shell note: if `npm` is aliased to another package manager on your machine, run `command npm` to reach the real npm.
- No Code node is hand-written: each is `export function run(input) { ... }` in `src/nodes/<name>.ts` — pure, no I/O, no clock — compiled by `npm run build:workflows`; `npm run check` rejects any Code node not listed in `scripts/lib/manifest.ts`'s `CODE_NODES`. Those sources use the ambient `DateTime` global (`src/globals.d.ts`) instead of importing Luxon, since the Code-node sandbox provides it but has neither `require` nor Node builtins, `fetch`, `window`, or `document`.
- n8n's Code-node Task Runner (`@n8n/task-runner`) runs generated `jsCode` after setting `Object.defineProperty = () => ({})`, a sandbox hardening measure. esbuild's own IIFE output attaches every named export through that same function, so without a fix every export would silently vanish and `__node.run` would come back `undefined` — see `scripts/build-workflows.ts`'s `hardenAgainstFrozenDefineProperty`, covered by a dedicated test that simulates the frozen sandbox (`tests/lib/code-node.ts`'s `runJsCode` freezes the same way). Don't remove it when touching the build, and don't upgrade `esbuild` past its exact pin in `package.json` without re-checking this patch still applies to its codegen.
- A Postgres query's SQL comments never contain `$n` (enforced by `npm run check`): n8n formats a query client-side before sending it, replacing every `$N` in the raw text — comments included, since it works on the text, not a parsed statement — so a bound value containing a newline can end a `--` comment and turn whatever follows into live SQL. Document a query parameter in the sticky note or a plain comment instead, never with its own `$n`.
- PHP: every file starts with `declare(strict_types=1);`. Class files under `plugin/moving-quote/src/` hold only declarations, with no `ABSPATH` guard, so PHPUnit loads them without WordPress; files that run code when loaded (`moving-quote.php`, `templates/quote-form.php`) start with `defined( 'ABSPATH' ) || exit;`, and `uninstall.php` starts with `defined( 'WP_UNINSTALL_PLUGIN' ) || exit;`. Pure classes (`Pricing\*`, `Settings\Defaults`, `Leads\LeadValidator`, the `Leads` value objects, …) never call a WordPress function — `Rest\Messages::field()` is the one exception, since it needs `__()` for translated field messages. `Frontend\Shortcode` and `templates/quote-form.php` are WordPress-coupled by design (rendering and enqueuing can't be pure), so they're covered by the stack suite instead of PHPUnit. PHPStan runs at level 9 with typed array shapes (`@param array{…}`, `@return iterable<string, array{…}>`) on every helper and data provider that touches an array.

## Guardrails

- Secrets live only in `.env` (gitignored) and n8n credentials — never in code, workflow JSON, or committed config. `scripts/init-env.ts` never prints a secret; neither does `scripts/setup-credentials.ts`, which detects which credentials already exist in n8n from a CLI export, never a decrypted one, and only ever logs a credential's name and id, never its `data`.
- Test data: emails use `example.com`; phone numbers use the prefix `5700000000`; customer names are invented. Everything in the repo is in English.
- `npm run setup` skips a credential whose `.env` values are blank, or one that already exists in n8n unless named with `--refresh <id>` — re-importing a credential replaces it, which would otherwise drop an interactive Google sign-in.
- Generated files (`plugin/moving-quote/assets/quote-form.js`, the Composer autoloader, each Code node's `jsCode`) are committed, and CI fails when they drift. Never edit them by hand. `quote-form.js` is regenerated with `npm run build:assets`; `plugin/moving-quote/vendor/` is regenerated with `npm run php -- composer autoload:plugin`; each Code node's `jsCode` is regenerated with `npm run build:workflows`; its `composer.json` pins an explicit `version` and `autoloader-suffix` so the generated files are identical across commits.
- Point tooling only at this repo's local n8n instance, never another instance. Validate workflows with an n8n-aware validation tool before importing them.
- **PR protocol.** Branch `task-NN-<slug>` from `main`. The implementer only commits; the controller pushes, opens the PR (summary, verification, review record), waits for green CI, then squash-merges.

## Definition of done

- `npm run typecheck && npm run lint && npm test` all pass locally — run this full gate before every commit that touches TypeScript. Also run `npm run build:assets -- --check` (and commit a fresh `npm run build:assets` if it fails) before every commit that touches `src/frontend/**`, and `npm run build:workflows -- --check && npm run check` before every commit that touches `workflows/`, `src/nodes/**`, or `scripts/lib/manifest.ts`.
- `npm run php -- composer check && npm run php -- composer audit` pass locally — run this full gate before every commit that touches PHP.
- `npm run test:stack` passes locally against a running stack — run this before every commit that touches `compose.yaml`, `setup.sh`, or `tests/stack/**`.
- No secrets anywhere in the diff or git history; `.env` and `config/config.json` are never committed.
- `README.md` (Status, What works now, and the quick start if commands changed) and this file are updated to match what the change actually adds.
- Commits follow Conventional Commits, on a branch named `task-NN-<slug>`.
