# Translations, languages and the switcher

English is the source language; Spanish (Colombia) is the one translation. Spanish lives only in `moving-quote-es_CO.po`, the theme's `site/theme/languages/es_CO.po`, in `map-lead.ts`'s `{ en, es }` `MESSAGES`, in `error-alert.ts`'s `{ en, es }` `ALERT_MESSAGES`, and in the Spanish page titles, excerpts and slugs (`setup.sh`'s `load_copy es_CO` and `load_slugs es`, `playground/blueprint.es.json`), never in plugin or theme logic. Spanish copy uses *usted* with customers, in a neutral Latin American, Colombian business register.

- **The plugin's strings.** Every user-visible PHP string goes through `__()`, `esc_html__()`, `esc_html_e()`, `_n()` (anything with a count), or `_x()` (context-dependent short strings: lead and delivery statuses, route column headings), with the `moving-quote` domain and a `/* translators: */` comment on any placeholder. PHPCS's `WordPress.WP.I18n` enforces the domain. `Plugin::boot()` loads it on `init`. The script has no gettext calls: its strings arrive translated through `data-config` (`Frontend\Shortcode::config()`), and estimates use the server's `display` text (`number_format_i18n()`).
- **The theme's strings.** The page copy lives in `site/theme/patterns/*.php`, every string through `esc_html_e()` or `esc_attr_e()` with the `chivabox` domain (PHPCS accepts both domains), loaded by `load_theme_textdomain()` from `site/theme/languages/` (a theme's catalogs are named `<locale>.po`). `scripts/i18n.ts`'s `TEXT_DOMAINS` lists both domains, and `pnpm run i18n` regenerates `chivabox.pot`, `es_CO.mo` and `es_CO.l10n.php` the same way it does the plugin's; `make-pot` also extracts each pattern's `Title` (context `Pattern title`).
- **Adding or changing a string.** Edit the PHP, bring the stack up, run `pnpm run i18n`, update `moving-quote-es_CO.po` (or the theme's `es_CO.po`) (no `fuzzy`, every plural form, the same placeholders and markup), run `pnpm run i18n` again, and commit all four files. `tests/i18n.test.ts` catches a missing, removed, empty, or fuzzy message or a changed placeholder or tag; CI's `Stack (WordPress)` job catches a stale `.pot`, `.mo`, or `.l10n.php`. The `.pot` has no `#: file:line` (`--no-location`), so only a changed string makes it stale.
- **Adding a language.** Copy the `.pot` to `moving-quote-<locale>.po`, fill the header (`Language`, `Plural-Forms`, and a fixed `POT-Creation-Date`, which keeps the compiled files byte-stable) and every message, run `pnpm run i18n`, and commit. The n8n emails need a new `MESSAGES` key and `normalizeLocale()` support.
- **The default language.** `SITE_LOCALE=es_CO ./setup.sh` (or in `.env`) makes Spanish the default: Polylang's default language and the site language (`WPLANG`). `./setup.sh` (or `SITE_LOCALE=en_US`) switches back. Both languages always exist. Each run rewrites the menu links it wrote under the other default (`relink_post()`, an exact match on the old path only), so after a switch each language's menu still points at its own pages; any other link stays as it is. Links inside the page copy need no rewrite: the patterns resolve them at render time with `chivabox_page_url()`. A site first set up in Spanish before the switcher has Spanish copy on its English-slug pages, which get tagged English: delete those three pages and `primary-navigation`, then rerun. The plugin's translations ship with it; core's `es_CO` pack (always installed by `setup.sh`) supplies WordPress's own strings and the thousands separators (`1.017.000`; without it, `1,017,000`).
- **The lead's language.** `LeadController` stores the page's language (see "The page's language" in [`api.md`](api.md#rest-behavior)) in `locale`, and the payload sends it. `parseLead()` reads it through `normalizeLocale()` (`es_CO`, `es-CO`, `es` → `es`; `en_US`, `en` → `en`; anything else, empty, or missing → `en`). The customer email follows the lead; the team email follows `config.json`'s `team_locale` (`en` or `es`, `en` when absent). An invalid `team_locale` never fails a lead or an alert: the team email and the operator alert fall back to English with a note, since config travels in each execution's input and a throw would block every retry. `parseTeamLocale()` stays strict for checking a config file.
  - **Deploy order:** publish the workflows (`pnpm run setup`) before updating the plugin. An older `lead-intake` answers a lead carrying `locale` with 422 (`hasOnlyKeys`), and WordPress retries until `failed`.

## Languages and the switcher

The demo site is bilingual through **Polylang** (free, from wordpress.org), pinned at exactly `3.9.1` in `setup.sh`'s `polylang_version`. Bump it deliberately, after reading its changelog; `tests/stack/wp/language-switcher.test.ts` asserts the version.

- **The plugin never depends on Polylang.** It calls `pll_get_post()` only behind `function_exists()`, and the `locale` query arg works with any multilingual plugin that sets the language per page. `tests/stack/wp/i18n.test.ts` deactivates Polylang and checks the plugin in Spanish through `WPLANG` alone.
- **Languages.** English (`en_US`, code `en`) and Spanish (`es_CO`, code `es`), in that order. `SITE_LOCALE` picks the default, served without a URL prefix; the other is under `/es/` or `/en/` (Polylang's defaults: the language as a directory, hidden for the default language, no browser detection).
- **Pages.** Each language has its own slugs, since Polylang (free) needs distinct ones: `home`/`inicio`, `get-a-quote`/`cotizar`, `thank-you`/`gracias`, `data-policy`/`politica-de-datos`, linked as translations. The data policy page is a demo sample, and `wp_page_for_privacy_policy` points at its English page, which the consent line links to (translated by `Frontend\Shortcode::privacy_url()`); `setup.sh` sets the option only when it's unset or points at a page that isn't published, so an owner's own choice survives a rerun. The front page is the default language's home; the other language's root redirects to that home's translation (`/es/` to `/es/inicio/`, or `/en/` to `/en/home/`). The menus' links are written for the default language by `lang_path()`, and rewritten by `relink_post()` when the default changes. Links inside the page copy come from the theme's `chivabox_page_url( $english_slug )`, which answers the page's translation in the visitor's language (`pll_get_post()` behind `function_exists()`), or the home page when the page is missing.
- **Menus and the switcher.** Polylang (free) doesn't translate `wp_navigation` posts, so `site/mu-plugins/translated-navigation.php` adds the type through Polylang's `pll_get_post_types` filter. The Chivabox header's navigation has no `ref`: it renders the most recently published menu, through a `WP_Query` Polylang then filters by the current language. `setup.sh` creates `primary-navigation` (English) and `navegacion-principal` (Spanish), each with Get a quote (the logo already links home) and `<!-- wp:polylang/navigation-language-switcher {"show_labels":"names"} /-->`, which renders English and Español, each link with `hreflang` and `lang`; the theme marks the current one (`.current-lang`) on a soft accent pill.
- **The tagline** is one option. `setup.sh` maps its stored value to each language's copy in Polylang's string translations (`PLL_MO`), since Polylang can keep the stored value when a new one is its own translation.
- **Polylang (free) has no WP-CLI commands.** `setup.sh` calls its PHP API through `wp eval-file -`: `PLL()->model->languages` (`add()`, `update_default()`), `pll_insert_post()`, `pll_set_post_language()`, `pll_save_post_translations()`, and `PLL_MO`. It also deletes `pll_activation_redirect`, so the first admin visit isn't sent to Polylang's setup wizard.

The Playground blueprints stay monolingual; see "The Playground blueprints" in [`testing.md`](testing.md#the-playground-blueprints).
