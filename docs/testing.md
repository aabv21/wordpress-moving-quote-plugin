# Test suites

This page lists every test suite in the repo: its command, what it covers, and how it stays deterministic and clean. It ends with what continuous integration (CI) actually runs and the guardrails that keep a local run from touching the owner's real Google account.

## Unit and frontend (Vitest)

**Command:** `pnpm test` (`vitest run`, config `vitest.config.ts`).

Covers every TypeScript module outside `tests/stack/`: `tests/frontend/*.test.ts` (the quote form's `debounce`, `latestOnly`, `uuidV4`, `postJson`, `form-state`, `estimate-display` — the display text and the panel outcome (`ready` or `error`, never one without the other's matching text) for an estimate result, and which field names should trigger a refetch — `reference`, which accepts only a well-formed `MQ-…` reference from a submission response and builds the thank-you redirect URL that carries it, and `estimate-fetch`, which proves a failed estimate is reported as an error with the placeholder text and a stale estimate response, resolved after a newer call's own response, never overwrites the newer result already displayed), `tests/nodes/*.test.ts` (the n8n Code-node sources: `parseLead`, including a missing, empty, or unknown `locale` falling back to `en`; `verify-request`; `map-lead`, including the customer email in each language, the team email in `team_locale` whatever the lead's language, an invalid `team_locale` (`ES`, `es_CO`, a number, …) never blocking the lead — the customer email still goes out in the lead's language and the team email in English with a one-line note — a lead with no usable locale getting an English customer email, and every `MESSAGES` entry present and non-empty in both languages; and `locale.ts`'s `normalizeLocale` and `parseTeamLocale`, including that `config/config.example.json` passes, and the never-throwing `teamLocaleOrDefault` `map-lead` uses) and `tests/nodes/lead-payload-parity.test.ts` (the TypeScript half of the PHP/TS payload parity corpus: `parseLead()` accepts every fixture in `tests/fixtures/lead-payloads/`, the exact bodies `Delivery\LeadPayload::body()` produces for each of 10 edge cases, proven PHP's own real output by `tests/php/Delivery/LeadPayloadParityTest.php`, and that the Spanish and empty-locale fixtures parse as `es` and `en`), `tests/i18n.test.ts` (the translations: the `.po` holds every `.pot` message and nothing the `.pot` dropped, every message is translated with every plural form filled and none fuzzy, each translation keeps its source's placeholders and HTML tags, and the committed `.l10n.php` and `.mo` carry every translation), `tests/tooling/gettext.test.ts` (the `.po` parser, the placeholder reader, and the `.pot` comparison that ignores only `POT-Creation-Date`), `tests/tooling/*.test.ts` and `tests/scripts/*.test.ts` (the workflow tooling CLIs), `tests/env-example.test.ts` and `tests/init-env.test.ts` (the `.env.example` template and `scripts/init-env.ts`'s generator), `tests/workflows.test.ts` (every committed workflow's pinned nodes, wiring, and settings, including `saveManualExecutions: false` on every file), `tests/playground.test.ts` (the three Playground blueprints, including that the English and Spanish ones carry `setup.sh`'s own copy for their language), `tests/db-migrate.test.ts` (migration ordering, `\getenv` extraction, the transaction-control guard, the role-name-clash guard, and the password-logging guard, against `scripts/db-migrate.ts` and `db/migrations/001_runtime_role.sql`/`db/init/01-app.sh` directly), `tests/check-db.test.ts` (the denial/grant/role-fact predicates, the one workflow statement `check-db` probes, and its generated psql script, against `scripts/check-db.ts`), and `tests/hygiene.test.ts` (every tracked file, read fresh from `git ls-files`, states its own reason instead of pointing at an external planning artifact — deliberately not finding-style IDs like `C1`, since those collide with legitimate text such as a C0 control-character reference; `pnpm-lock.yaml`, this test file itself, and the generated `quote-form.js` are excluded as carrying no authored prose). `tests/lib/code-node.ts` isn't a test file itself — it's the shared Code-node sandbox runner the Code-node and tooling tests above import.

**Staying deterministic and clean:** `vitest.config.ts` excludes `tests/stack/**` explicitly, so this run never needs Docker or a live stack. `tests/setup.ts` provides the ambient `DateTime` global the Code-node sandbox exposes at runtime, so a Code-node source under test sees the same global shape it would in n8n. No test in this suite opens a network connection; `tests/init-env.test.ts` and `tests/tooling/build-workflows.test.ts` are the exception to "no filesystem access" — both write to a fresh `mkdtempSync` directory under the OS temp dir, never the repo itself, so a run never leaves anything behind to clean up.

## Tooling and workflow hygiene

Part of the same `pnpm test` run above (`tests/tooling/`, `tests/scripts/`, `tests/workflows.test.ts`), called out separately here because it's a distinct concern: these tests don't exercise application logic, they exercise the tools that keep the committed workflow JSON reviewable and reproducible.

- `tests/tooling/build-workflows.test.ts`, `tests/tooling/check-workflows.test.ts` — the Code-node build and the hygiene checker, each against `tests/fixtures/workflows/` (`clean.json` plus one defect per other fixture).
- `tests/tooling/credentials.test.ts`, `tests/tooling/google-credential-ids.test.ts` — the credential-import plan (skip existing, `--refresh`, blank `.env` values) and the pure `googleCredentialIds()` helper, with no `.env` dependency.
- `tests/tooling/import-workflows.test.ts` — `missingWorkflowIds()`, the pure function behind `pnpm run setup`'s post-import verification: given the manifest's workflow IDs and the set actually seen in n8n, it reports exactly which are still missing, in manifest order.
- `tests/tooling/poll.test.ts` — the bounded execution-lookup poll (`tests/stack/lib/poll.ts`), unit-tested directly against an injected lookup function rather than a live stack, even though its caller (`tests/stack/lib/execution-data.ts`) is a stack-only module.
- `tests/tooling/compose.test.ts` — `scripts/lib/compose.ts`'s `compose()` helper, with `node:child_process`'s `spawn` mocked: a successful and a failing exit both resolve/reject with the captured stdout and stderr, a stdin error (e.g. `EPIPE`) rejects instead of throwing, a `spawn` error rejects instead of throwing, and a call with no `input` never spawns at all (it uses `execFile` instead).
- `tests/scripts/check-workflows-cli.test.ts` — the CLI's per-fixture output and exit code.
- `tests/workflows.test.ts` — every committed workflow file's pinned node parameters, IF conditions, Postgres `typeVersion`, retry settings, and `errorWorkflow` wiring, so a hand edit to `workflows/*.json` that drifts from the generated or reviewed form fails here before it fails anywhere live.

**The commands these build and check tools exercise, which CI runs directly (not through a test file):**

- `pnpm run build:workflows -- --check` — fails if a Code node's committed `jsCode` doesn't match a fresh build of its `src/nodes/*.ts` source. Runs in the `quality` job.
- `pnpm run check` — the hygiene checker against `workflows/` itself (pinned data, required settings, no literal secrets, known credential IDs, documented Code nodes, required retries, safe Postgres parameters, a sticky note per workflow). Runs in the `quality` job.

**Staying deterministic and clean:** every hygiene-check case runs against a static fixture file, never the live stack; `tests/fixtures/nodes/double.ts` is a one-line fixture Code-node source shared by the fixtures and tooling tests, so a build test never depends on a real `src/nodes/*.ts` file changing underneath it.

## Supply-chain and CI hardening

Part of the same `pnpm test` run (`tests/supply-chain.test.ts`), checking the settings that keep a dependency or a CI step from running unpinned or unreviewed code, against the real, effective config rather than just the text that sets it:

- **pnpm.** `pnpm config list --json` (not just `pnpm-workspace.yaml`'s text, so a misspelled or ignored key fails here) carries `minimumReleaseAge` of at least 4,320 minutes (3 days) with `minimumReleaseAgeExclude` emptied out (pnpm 11 ships a built-in n8n exemption this repo overrides), `trustPolicy: no-downgrade`, `blockExoticSubdeps`, `strictDepBuilds`, and `engineStrict` all on, and `dangerouslyAllowAllBuilds` off; `trustPolicyExclude` holds exactly the three owner-approved `@octokit/*` pins (an exact `name@version` each, never a bare name); `package.json`'s `packageManager` pins an exact `pnpm@11.x.y`; `package-lock.json` doesn't exist; and no tracked file (other than the test itself) still teaches any `npm` or `npx` subcommand, since this repo's own pnpm alias convention replaces all of them.
- **Docker image pinning.** Every `image:` line in `compose.yaml` and `compose.queue.yaml`, and every `FROM`/`COPY --from` line in `docker/php/Dockerfile`, is pinned by `@sha256:` digest; so is every `docker run` image reference across every file in `.github/workflows/`.
- **Container hardening.** Reading the merged, effective Compose config (`docker compose … config --format json`, not the raw YAML, so `n8n-worker`'s settings inherited through `extends` are checked too): every long-running service (`db`, `wordpress`, `wpcli`, `cron`, `postgres`, `n8n`, `redis`, `n8n-worker`) sets `security_opt: no-new-privileges:true` (the one-shot `php` tools container is excluded); only `n8n` and `n8n-worker` drop every Linux capability (`cap_drop: ALL`) — the other services switch users internally at startup and need a capability this repo hasn't proven safe to drop per image yet.
- **Composer policy.** `composer.json`'s `config.policy.advisories.block` and `config.policy.abandoned.audit` are both set to fail the build on an insecure or abandoned package; its cooldown period is at least 3 days; there's no deprecated `config.audit` key; `config.allow-plugins` is an object (never a bare `true`) listing only installed plugins; and `minimum-stability`/`prefer-stable` keep the project on stable releases.
- **zizmor.** `.github/workflows/ci.yml` installs it with `pip install --require-hashes -r .github/zizmor-requirements.txt`, and that requirements file pins `zizmor==1.31.1` with at least one `--hash=sha256:…` line.

**Staying deterministic and clean:** every check reads real config (pnpm's own effective settings, the merged Compose config, the committed `composer.json`/workflow files) rather than re-asserting a copy of a value, so a change to the underlying setting is what the test actually verifies, not a restatement of it.

## PHP (PHPCS, PHPStan level 9, PHPUnit)

**Command:** `pnpm run php composer check` (runs `composer lint`, then `composer analyse`, then `composer test`, inside the `php` tools container — there is no local `php` or `composer`). `pnpm run php composer audit` checks dependencies separately.

- **`composer lint`** — PHPCS with `WordPress-Extra` plus `PHPCompatibilityWP` (`testVersion` `8.3-`, `minimum_wp_version` `7.0`), over `plugin/moving-quote`, excluding `vendor/` and `assets/`. Two sniffs are excluded with a one-line reason each (`WordPress.Files.FileName` conflicts with PSR-4 file names; `Universal.Arrays.DisallowShortArraySyntax` is dropped because the codebase uses modern `[]` syntax throughout). `WordPress.DB.DirectDatabaseQuery` is excluded only for `src/Leads/LeadRepository.php` and `src/Install/*`, where direct `$wpdb` queries are the point.
- **`composer analyse`** — PHPStan level 9 over `plugin/moving-quote/src`, `moving-quote.php`, `uninstall.php`, and `tests/php`, with `--memory-limit=1G`. Level 9 requires every array touched by a typed helper or data provider to carry an explicit shape (`@param array{…}`).
- **`composer test`** — PHPUnit 11.5, `failOnWarning`, `failOnNotice`, `failOnDeprecation`, and `failOnRisky` all on, over `tests/php/**/*Test.php`, covering every pure class: `Pricing\Calculator` and `Pricing\DistanceTable`, `Settings\SettingsSanitizer`, `Leads\LeadValidator` and `Leads\LeadRecord` (including `is_reference()`, the one gate between the thank-you page's query string and its output), the pure `Delivery` classes (`JwtSigner`, `LeadPayload`, `ResponseCheck`, `Backoff`, `SyncTransition`), the pure `Admin\CsvEscaper` and `Admin\LeadCsv`, and `Security\RateLimiter::normalize_ip()` (`tests/php/Security/RateLimiterTest.php`) — the one pure, WordPress-free piece of that otherwise WordPress-coupled class: an IPv4 address (including an IPv4-mapped IPv6 one) is returned unchanged, and two IPv6 addresses inside the same /64 normalize to the same value while two addresses in different /64s don't. `Delivery\LeadPayloadParityTest` builds the 10 edge-case `LeadRecord`s in `tests/fixtures/lead-payloads/` and asserts `LeadPayload::body()` matches each fixture byte for byte — the PHP half of the PHP/TS payload parity corpus, proving the committed fixtures are PHP's own real output rather than a hand-written guess for `tests/nodes/lead-payload-parity.test.ts` to check against.

**Staying deterministic and clean:** PHPUnit here never bootstraps WordPress — every class under test lives in `plugin/moving-quote/src/` with no `ABSPATH` guard, specifically so PHPUnit can load it standalone. Every test case is exact (an input and an expected output), not a range check, including the full backoff schedule and every `SyncTransition` state. CI also runs an autoloader-drift check (`composer autoload:plugin`, then `git diff --exit-code -- plugin/moving-quote/vendor`) to catch a PSR-4 mapping change that wasn't followed by a regenerated, committed autoloader.

## The WordPress stack suite

**Command:** `pnpm run test:stack:wp` (`vitest run --config vitest.stack.config.ts tests/stack/wp`). Needs `docker compose up -d --wait db wordpress wpcli` and `./setup.sh` already run.

Covers everything WordPress-coupled that PHPUnit can't reach without a real WordPress: `tests/stack/wp/install.test.ts` (activation, deactivation, upgrade — including a schema-version-1 table gaining the `locale` column in place, its existing row untouched — uninstall — including that uninstall also clears the rate-limited-submissions counter transient, and that a Multisite-targeted activation call still completes on this single-site stack), `tests/stack/wp/settings.test.ts` (Colombian-formatted amounts, invalid-input rejection), `tests/stack/wp/quote-api.test.ts` (the estimate and lead REST endpoints, rate limiting, nonces, the rate limiter's fail-closed lock behavior, and the phone and email messages that name a valid value), `tests/stack/wp/quote-page.test.ts` (the rendered shortcode and its config, the honeypot's `aria-hidden` wrapper, `[moving_quote_reference]` showing a well-formed reference and rendering nothing for a missing, malformed, or markup-carrying one, a submission signed with a nonce scraped from the rendered page — plain `fetch` calls, not a real browser — and the move-date input's `min` matching the server's own America/Bogota "today"), `tests/stack/wp/admin.test.ts` (the Leads list, including each row's labelled status `<select>`, status updates, per-row delete, CSV export — including that an unparseable row is skipped rather than fataling the page or export, that the export doesn't truncate when a batch contains one bad row, that no `<form>` is left open when the rendered page's list table starts, so the first row's own status form is never folded into an outer one — retry, the stuck-delivery notice and its won/lost exclusion, and the rate-limited-submissions notice), `tests/stack/wp/privacy.test.ts` (the registered personal-data exporter and eraser, called through `apply_filters('wp_privacy_personal_data_exporters'/'erasers', [])` so registration itself is exercised: every lead field exported, multiple leads sharing one email, a lead with an unparseable `status` still erasable even though the exporter would skip it, and that erasing an existing lead reports `items_retained` with a message naming its own `MQ-…` reference — proof the eraser warns about copies it can't reach in the Sheet, the sent emails, and n8n's own execution data), `tests/stack/wp/delivery.test.ts` (signed delivery, including the payload's `locale`, and the outbox's retries and claim/lease guards), `tests/stack/wp/i18n.test.ts` (the site in Spanish: it sets `WPLANG` to `es_CO` for the file and restores the previous value afterward, then asserts the quote form renders in Spanish with no English source string left in it — every untranslated-would-show `msgid` from the `.po` is checked — its script's `data-config` messages are Spanish, a REST 422 and its field messages are Spanish, the estimate uses WordPress's own thousands separator for that language, a lead submitted then stores `es_CO`, the thank-you reference line is Spanish, and the Leads and Settings admin pages are Spanish), and `tests/stack/wp/runtime.test.ts` (WordPress itself after `setup.sh`: installed, Bogotá timezone, the default theme and the plugin active, each expected page and the `primary-navigation` menu created once, and the theme's header navigation using that menu instead of a list of every page).

**Staying deterministic and clean:**

- `tests/stack/global-setup.ts` stops the `cron` sidecar for the whole run, so its background `wp cron event run --due-now` loop can't race a test file's own assertions about exactly which leads were retried when — restarting it afterward only if it was running before.
- `tests/stack/lib/stack.ts`'s `sqlWp()` never uses `wp db query`: the `wpcli` image's bundled MariaDB client isn't guaranteed compatible with MySQL 8.4's wire protocol, so it runs `wp eval-file -` instead, executing PHP through WordPress's own `$wpdb` — the same client the plugin itself uses at runtime.
- `tests/stack/lib/leads.ts` tracks every `request_uuid` a test mints and calls `deleteCreatedLeads()` in each file's `afterAll`, since a saved lead is a real delivery attempt and cron keeps retrying a pending one for hours if it's left behind.
- `tests/stack/wp/delivery.test.ts` additionally parks every other pending row (`next_attempt_at` far in the future) before and after each case, and filters its receiver's recorded requests by the body's own `request_uuid` rather than assuming "the last request" is its own — a second layer of defense on top of stopping `cron`, so the file stays correct even under a manual or partial run where that sidecar might still be running.
- `tests/stack/lib/stack.ts`'s `disableDelivery()` patches `webhook_url` to `''` and returns a restore function, for a file whose leads must never actually reach the configured n8n URL.

## The n8n stack suite

**Command:** `pnpm run test:stack` runs the full stack suite including this half; there's no separate `pnpm run test:stack:n8n` script, so run `vitest run --config vitest.stack.config.ts tests/stack/n8n` directly to scope it alone. Needs the whole stack (MySQL, WordPress, WP-CLI, Postgres, n8n) healthy and `./setup.sh` already run.

Covers the WordPress-to-n8n handoff and n8n's own workflows: `tests/stack/n8n/intake.test.ts` (JWT verification failures, the idempotency gate, concurrent-delivery dedupe, the soft-delete-for-purge check on a successful run), `tests/stack/n8n/process-lead.test.ts` (a read-only decode of a real execution proving "Map lead" ran and the chain reached "Append lead row", and that a Spanish lead's customer email comes out in Spanish inside n8n's own Code-node sandbox: Colombian number grouping and a Spanish date, which depend on that sandbox's own `Intl` locale data), `tests/stack/n8n/end-to-end.test.ts` (a lead sent from the real WordPress path through to n8n, including an n8n-down-then-recovered case and a wrong-secret-then-restored case), and `tests/stack/n8n/runtime.test.ts` (n8n's own health, the Postgres role isolation between the `app` and `n8n` databases, `processed_events` starting empty, and a full run of `node scripts/check-db.ts` against the real stack — printing its output on failure instead of just the bare exit code).

**Staying deterministic and clean:**

- `tests/stack/lib/execution-data.ts` decodes a stored execution's `flatted`-encoded data read-only, through n8n's own bundled `flatted` package inside the container, with its own polling loop (`tests/stack/lib/poll.ts`'s `pollForExecutionId()`) factored out as side-effect-free so it can be unit-tested directly (see "Tooling and workflow hygiene" above) without pulling in the live-stack module.
- `tests/stack/lib/jwt.ts`'s `signHs256()` and `decodeVerified()` sign and verify an HS256 JWT independently with `node:crypto`, and `decodeVerified()` is asserted with `not.toBeNull()` — never by comparing a secret value directly — so a test proves the signature is valid without ever asserting equality on sensitive material.
- **The live-Google skip guard.** Every case that would hand a test lead to `process-lead` checks `googleCredentialsConfigured()` first (`tests/stack/lib/stack.ts`): it lists n8n's credential IDs through a non-decrypted CLI export — the same way `pnpm run setup` itself checks — and skips with a console message once either Google credential already exists. `tests/stack/n8n/end-to-end.test.ts` and `tests/stack/n8n/process-lead.test.ts` skip their entire `describe` block this way; `tests/stack/n8n/intake.test.ts` marks only its accepted-lead cases with `it.skipIf(...)`, since its rejection cases and its missing-config case never reach `process-lead` at all. Without this guard, running the suite after the owner wires in the real Google account would append a test row to the real `Moving leads` sheet and email the real team on every run.

## The queue-mode run

**Command:** `docker compose -f compose.yaml -f compose.queue.yaml up -d --wait --scale n8n-worker=2`, then `vitest run --config vitest.stack.config.ts tests/stack/n8n/intake.test.ts` against that stack. Return with `docker compose -f compose.yaml -f compose.queue.yaml down && docker compose up -d --wait`.

Not a separate test file: it's the same `tests/stack/n8n/intake.test.ts` suite run against a queue-mode stack instead of the regular single-process one, to prove the JWT check, the raw-body hash, and the idempotency gate all work identically when a worker — not the main process — executes the workflow. Verified: the intake suite passed 13/13 with two workers running, including the five-concurrent-deliveries case giving exactly one `accepted`, and the worker containers' own logs showed them running the executions.

**Staying deterministic and clean:** `compose.queue.yaml`'s `n8n-worker` service `extends` `compose.yaml`'s own `n8n` service, so it shares the same encryption key, database settings, and read-only `/files` mounts — nothing queue-specific to keep in sync by hand. The missing-config test case in this suite waits until n8n and every running worker have seen the file change, since in queue mode a worker (not the main process) is what actually executes a waiting run.

## Playground

**Command:** no live server command is part of the gate; `tests/playground.test.ts` (part of `pnpm test`) parses all three blueprint files and asserts the English two's steps stay deep-equal after the first (which differs only in install source), and that `playground/blueprint.es.json` is the public one plus a `setSiteLanguage` step, with only the copy changed. The live check is manual: `pnpm dlx @wp-playground/cli@3.1.61 server --php=8.3 --port=9400 --mount=./plugin/moving-quote:/wordpress/wp-content/plugins/moving-quote --blueprint=playground/blueprint.local.json`.

Covers the plugin's behavior on WordPress Playground's SQLite-backed WordPress, with no server to install: the estimate endpoint, the three-step form, a submission, and the Leads admin page. Verified locally against `@wp-playground/cli@3.1.61`: the estimate endpoint returned the documented response for an apartment move from Barranquilla to Cartagena; in the browser, the form showed the same live estimate, a submission redirected to `/thank-you/`, and Moving quotes → Leads listed it with Delivery "Pending (0 attempts)"; the CLI's own stdout showed no PHP errors or warnings, and the browser's console showed none beyond WordPress core's own standard jQuery Migrate notice.

**One real gap this surfaced and fixed:** `Security\RateLimiter::acquire_lock()` originally checked only for MySQL's exact `GET_LOCK()` success value `'1'`. Playground's SQLite translator answers the same, meaningless-there lock as `'1=1'` instead, so every `estimate` and `submit` request was being rejected as rate-limited on Playground, breaking the form. The check now also accepts `'1=1'`; verified against both the real MySQL stack (the fail-closed and concurrent-burst cases in `tests/stack/wp/quote-api.test.ts` still pass) and Playground.

`tests/stack/wp/i18n.test.ts` writes `WPLANG` straight through `$wpdb` rather than `update_option()`, whose sanitizer only accepts a language with an installed core pack: the stack never downloads one, since the plugin's own translations ship with it. It reads the previous value first and puts it back (or removes the row) in `afterAll`, and every other stack file runs in English, before or after it, never alongside it (`fileParallelism: false`).

**Staying deterministic and clean:** `@wp-playground/cli` is pinned at exactly `3.1.61`, named above, so a version drift in Playground itself can't silently change what this check verifies. Each `server` run starts from a throwaway in-memory virtual filesystem — nothing persists between runs, and nothing written during a manual check needs cleanup. `tests/playground.test.ts` is the one piece of this that runs automatically: it compares `playground/blueprint.json` and `playground/blueprint.local.json` structurally (`steps.slice(1)` deep-equal) so the two blueprints can't drift apart from each other, and checks the English and Spanish blueprints against `setup.sh`'s own copy for each language, without needing the CLI itself. The Spanish blueprint itself isn't run live: it installs from GitHub, so it waits for the repository to be public like the English public one.

## The quote form's accessibility and screenshots (manual)

**Command:** none in the gate. Start Playground with the command above, then drive a real browser (Playwright) through every screen at 1280 × 800 and 390 × 844: the form's three steps with a live estimate, a validation error (a server 422), the thank-you page, and Moving quotes → Leads. On each, inject axe-core with a script tag and run `axe.run()`. axe is fetched for the check only (for example `npm pack axe-core@4` into a scratch directory, a version past the repo's 3-day release-age rule) and is never a dependency of this repo.

Covers what no automated suite here can see: the rendered contrast of every state, focus visibility, the keyboard path (Tab through every control, Enter in a field advances a step, Space toggles a checkbox, Enter on the submit button reaches the thank-you page), no horizontal scroll at 390 px, and the form inside a second bundled theme (Twenty Twenty-Four) at 1280 px. The target is zero serious or critical violations in the plugin's own markup. Last run (axe-core 4.14.0): zero violations of any impact on every front-end screen at both widths, in both themes. On the Leads screen the plugin's own content (`#wpbody-content`) is clean at both widths; the full page still reports WordPress core's admin chrome (a `label-content-name-mismatch` on the Collapse Menu button at 1280 px and `aria-allowed-role` on admin-bar items), which this plugin doesn't render.

**Keeping the screenshots honest:** `docs/screenshots/` is retaken in the same session as that check, from the committed markup and stylesheet, and optimized to stay under about 300 KB per file. Retake it whenever either one changes.

## What CI runs

| CI job | What it runs |
|---|---|
| `quality` | `pnpm install --frozen-lockfile`, `typecheck`, `lint`, `test` (the full Vitest suite above, minus `tests/stack/`), `build:assets -- --check`, `build:workflows -- --check`, `check`, ShellCheck on every `*.sh`, then `composer validate --strict`, `composer install`, `composer audit --locked --abandoned=fail`, `composer lint`, `composer analyse`, `composer test`, and the autoloader drift check. |
| `security` | gitleaks in git mode over the full history, `pnpm audit --audit-level=high`, `composer audit --locked --abandoned=fail`. |
| `actions` | actionlint and zizmor against the workflow files themselves. |
| `stack` | `pnpm install --frozen-lockfile`, `node scripts/init-env.ts`, `cp config/config.example.json config/config.json`, `docker compose up -d --wait db wordpress wpcli postgres n8n`, `pnpm run i18n -- --check` (regenerates the `.pot` with the `wpcli` container's own pinned WP-CLI and diffs it against the committed one, ignoring `POT-Creation-Date`, and rebuilds the `.mo` and `.l10n.php` from the committed `.po` byte for byte; no network), `./setup.sh`, `pnpm run setup`, then **the full `pnpm run test:stack`** — both `tests/stack/wp/` and `tests/stack/n8n/`. The whole job takes about 7 minutes on GitHub's `ubuntu-latest` runner: about 1.5 minutes to pull images and start the stack, and about 4 minutes for the suite. Its `timeout-minutes` is 20. |
| `codeql` | `javascript-typescript` only (`codeql.yml:32`), gated on the repository being public. PHP has no CodeQL support here; the WPCS security sniffs and PHPStan level 9 cover it instead. |

**What's still not automated.** The `stack` job now boots the whole stack (MySQL, WordPress, WP-CLI, Postgres, n8n) and runs the full suite, the n8n half included — a change that breaks `lead-intake` or `process-lead` fails CI, not just a local run. CI has no Google credential, so every case that would reach `process-lead` (see "The live-Google skip guard" above) runs rather than skips, and asserts the chain reaches `Append lead row` and fails there on the missing credential — proof the hand-off actually executes, without ever touching a real Google account. Two things still need the owner's own accounts or a separate stack and stay manual: the queue-mode run (needs Redis and `n8n-worker`, and would double the job's services) and the Playground live check (needs a live `pnpm dlx` process). Both are run locally and recorded in each task's PR description.

## The rule: unit tests never import `.env`-loading modules

`tests/stack/lib/stack.ts` calls `process.loadEnvFile('.env')` at import time. CI's `quality` job runs `pnpm test` with no `.env` file present at all — only the `stack` job runs `node scripts/init-env.ts` first — so any test file outside `tests/stack/` that imported `stack.ts`, directly or transitively, would throw on import and fail the whole `quality` job.

The rule this repo follows: a helper two or more stack-test files need, with no dependency on the live stack itself, belongs in its own side-effect-free module instead (for example `tests/stack/lib/poll.ts`), so a unit test can import it directly without pulling in `stack.ts`. This rule is also stated in `AGENTS.md`'s Conventions section.

## Deferred live checks

Two things stay outside every suite above, because they need the owner's own accounts, not just the local stack:

- **Sheets and Gmail.** Every stack-test case that would reach `process-lead` skips itself once the owner's real Google credentials are configured in n8n (see "The live-Google skip guard" above). The actual appended row, the two sent emails, and a forced failure's alert email are verified once, by hand, in one session with the owner present, not by an automated suite — see the deferred live checks listed in the repository's README.
- **The public Playground link.** `playground/blueprint.json`'s GitHub-install path (as opposed to the local `--mount` path this page's Playground section covers) only works once the repository is public, so it's checked once after publication, not on every change.
