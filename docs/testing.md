# Test suites

This page lists every test suite in the repo: its command, what it covers, and how it stays deterministic and clean. It ends with what continuous integration (CI) actually runs and the guardrails that keep a local run from touching the owner's real Google account.

## Unit and frontend (Vitest)

**Command:** `pnpm test` (`vitest run`, config `vitest.config.ts`).

Covers every TypeScript module outside `tests/stack/`:

- `tests/frontend/*.test.ts`: the quote form's `debounce`, `latestOnly`, `uuidV4`, `postJson`, `form-state`, `estimate-display` (the display text and the panel outcome, `ready` or `error`, never one without the other's matching text, for an estimate result, and which field names should trigger a refetch); `reference` (accepts only a well-formed `MQ-…` reference from a submission response and builds the thank-you redirect URL that carries it); `summary-store` (reads back the thank-you summary only for the same reference and returns null for broken JSON, a missing or non-string field, or a storage that throws); and `estimate-fetch` (a failed estimate is reported as an error with the placeholder text, and a stale estimate response, resolved after a newer call's own response, never overwrites the newer result already displayed).
- `tests/nodes/*.test.ts`: the n8n Code-node sources: `parseLead`, including a missing, empty, or unknown `locale` falling back to `en`, a missing `contact` reading as blank numbers, and a contact number that isn't 10 to 15 digits or an extra key in `contact` rejected; `verify-request`; `map-lead`, including the customer email in each language (the brand header, the estimate figure, the five detail rows, the call and WhatsApp line only when the business numbers are set, a crafted name escaped inside the table, and `formatPhoneDisplay()` matching the plugin's display), the team email in `team_locale` whatever the lead's language, an invalid `team_locale` (`ES`, `es_CO`, a number, …) never blocking the lead (the customer email still goes out in the lead's language and the team email in English with a one-line note), a lead with no usable locale getting an English customer email, and every `MESSAGES` entry present and non-empty in both languages; and `locale.ts`'s `normalizeLocale` and `parseTeamLocale`, including that `config/config.example.json` passes, and the never-throwing `teamLocaleOrDefault` `map-lead` uses; `error-alert`, the operator alert: the exact English and Spanish copy, the fallbacks for a trigger failure with no `execution` key and for an empty payload, an invalid `team_locale` giving English with the note as the last line, a line break in the workflow name kept out of the subject, a payload of the wrong shape never throwing, and the committed `Compose alert` `jsCode` giving the same alert in the Code-node sandbox; `control-characters-parity`, which rebuilds `LeadValidator::CONTROL_CHARACTER_PATTERN` from the PHP source and checks it matches `lead.ts`'s `CONTROL_CHARACTER_RE` for every code point from 0 to 0xFFFF, and that `oneLine()` replaces exactly that set; and `map-lead`'s row ending with `request_uuid`, with two leads sharing a reference getting different sheet match keys.
- `tests/nodes/lead-payload-parity.test.ts`: the TypeScript half of the PHP/TS payload parity corpus: `parseLead()` accepts every fixture in `tests/fixtures/lead-payloads/`, the exact bodies `Delivery\LeadPayload::body()` produces for each of 11 edge cases, proven PHP's own real output by `tests/php/Delivery/LeadPayloadParityTest.php`, and that the Spanish and empty-locale fixtures parse as `es` and `en`.
- `tests/nodes/email-rule-parity.test.ts` and `tests/php/Leads/EmailRuleTest.php`: both read `tests/fixtures/email-cases.json`, so `isSimpleEmail()` and `Leads\EmailRule::is_simple()` agree on every address.
- `tests/constants.test.ts`: the business time zone and the currency are named once per language (`Plugin::TIMEZONE`, `Estimate::CURRENCY`, and `BUSINESS_TIMEZONE`, `CURRENCY` in `src/nodes/locale.ts`).
- `tests/retention.test.ts`: the eraser's retention days match n8n's `EXECUTIONS_DATA_MAX_AGE` in `compose.yaml`.
- `tests/tooling/no-cli-imports.test.ts`: no script imports another CLI; shared code lives in `scripts/lib/`.
- `tests/i18n.test.ts`: the translations, for both text domains in `scripts/i18n.ts`'s `TEXT_DOMAINS`, the plugin's and the theme's: the `.po` holds every `.pot` message and nothing the `.pot` dropped, every message is translated with every plural form filled and none fuzzy, each translation keeps its source's placeholders and HTML tags, and the committed `.l10n.php` and `.mo` carry every translation.
- `tests/tooling/gettext.test.ts`: the `.po` parser, the placeholder reader, and the `.pot` comparison that ignores only `POT-Creation-Date`.
- `tests/tooling/*.test.ts` and `tests/scripts/*.test.ts`: the workflow tooling CLIs (detailed under "Tooling and workflow hygiene").
- `tests/env-example.test.ts` and `tests/init-env.test.ts`: the `.env.example` template and `scripts/init-env.ts`'s generator.
- `tests/workflows.test.ts`: every committed workflow's pinned nodes, wiring, and settings, including `saveManualExecutions: false` on every file, "Append lead row" as `appendOrUpdate` matched on `request_uuid`, and `error-handler`'s Alert input → Compose alert → Email operator chain.
- `tests/ci.test.ts`: the CI split: the two stack halves don't wait on each other, only the WordPress half checks translations, only the n8n half copies `config.json` and runs `pnpm run setup`, the `Stack` gate's own `run` line executed under `bash` for every combination of `success`, `failure`, `cancelled`, and `skipped` so it passes only when both halves succeeded, and CodeQL's `actions` language.
- `tests/docs.test.ts`: `AGENTS.md` stays under 170 lines and 14,000 bytes, `docs/api.md` names every REST route, admin-post action, shortcode and webhook path the code registers, each repeated fact has one owning file, no em dash in the agent docs, no pointer to an `AGENTS.md` section that is gone, and (once the diagrams exist) every archify diagram is cited by the README, `AGENTS.md` and `docs/architecture.md`.
- `tests/readme.test.ts`: the README's section order, a quick start of five commands or fewer, the settings page's name, and every relative Markdown link in the README, `AGENTS.md`, `CONTRIBUTING.md`, and `docs/*.md` resolving to a file.
- `tests/versions.test.ts`: the plugin header's `Version:`, `Plugin::VERSION`, and the plugin's `composer.json` agree; the docs name an n8n patch only as the version a claim was checked against, and never pin a Redis version, so a Dependabot patch bump never makes them wrong.
- `tests/playground.test.ts`: the three Playground blueprints: the public ones install the plugin and the theme from GitHub, the local one activates the mounted theme, every page step writes a `chivabox` pattern reference, and the English and Spanish ones carry `setup.sh`'s own copy for their language and its business details.
- `tests/db-migrate.test.ts`: migration ordering, `\getenv` extraction, the transaction-control guard, the role-name-clash guard, and the password-logging guard, against `scripts/db-migrate.ts` and `db/migrations/001_runtime_role.sql`/`db/init/01-app.sh` directly.
- `tests/check-db.test.ts`: the denial/grant/role-fact predicates, the one workflow statement `check-db` probes, and its generated psql script, against `scripts/check-db.ts`.
- `tests/plugin-styles.test.ts`: the plugin's stylesheet never reads a `--wp--preset` value and gives every color token a literal default, so another theme can't recolor the form.
- `tests/hygiene.test.ts`: every tracked file, read fresh from `git ls-files`, states its own reason instead of pointing at an external planning artifact (deliberately not finding-style IDs like `C1`, since those collide with legitimate text such as a C0 control-character reference); `pnpm-lock.yaml`, this test file itself, and the generated `quote-form.js` and `thank-you.js` are excluded as carrying no authored prose.
- `tests/lib/code-node.ts` isn't a test file: it's the shared Code-node sandbox runner the Code-node and tooling tests above import.

**Staying deterministic and clean:** `vitest.config.ts` excludes `tests/stack/**` explicitly, so this run never needs Docker or a live stack. `tests/setup.ts` provides the ambient `DateTime` global the Code-node sandbox exposes at runtime, so a Code-node source under test sees the same global shape it would in n8n. No test in this suite opens a network connection; `tests/init-env.test.ts` and `tests/tooling/build-workflows.test.ts` are the exception to "no filesystem access": both write to a fresh `mkdtempSync` directory under the OS temp dir, never the repo itself, so a run never leaves anything behind to clean up.

## Quote form in a DOM (happy-dom)

**Command:** `pnpm test tests/dom` (also part of `pnpm test`). Type-checked by `pnpm run typecheck` under `tests/dom/tsconfig.json`, which adds the DOM lib.

`tests/dom/quote-form.test.ts` runs in happy-dom (pinned exactly as a devDependency) and imports the real, unchanged `src/frontend/quote-form.ts` against `tests/dom/fixtures/quote-form.html`, the template's markup rendered in English. It covers: the first step shown with `aria-current` on its marker; Next showing step 2 and focusing its legend, and staying put with a required field empty; Enter before the last step meaning Next, with nothing posted; three quick step-1 changes making one estimate call after 300 ms and showing its display text; typing in name, phone, or email scheduling no estimate call; a failed estimate showing the dash and its error; a 500 or a 404 showing the "our side" message, not the connection one; submit disabling the button and showing "Sending…", with a second click sending nothing; a 201 redirecting to the thank-you URL with `?reference=`, or, with no thank-you page, showing the inline success and focusing it; a 422 returning to the first step with the field marked invalid and focused; a 403, a 429, and a network failure each showing its message and re-enabling the button; a retry after a 429 reusing the same `submission_id`, a form rendered with both cities preselected asking for one estimate on load (and one with none asking for nothing), an empty estimate value with the hint before any price (never a dash), the summary's route, date and extras following the fields, a 201 saving the route, date and price in `sessionStorage` before it redirects, the inline success hiding the summary too, and the phone field described by its example and its error, the thank-you summary taking the price from the 201's `estimate.display` rather than the panel, the summary date in the page's language (`15/12/2026` in Spanish), and each placeholder line marked `data-empty` until filled. `tests/dom/thank-you.test.ts` loads `src/frontend/thank-you.ts` against `tests/dom/fixtures/thank-you.html`, the `[moving_quote_thanks]` card: it fills the summary only when the stored reference matches the page's, and renders stored markup as text.

**Staying deterministic and clean:** fake timers drive the 300 ms debounce, `fetch` is stubbed per test with `vi.stubGlobal`, `window.location.assign` is spied on, and `vi.resetModules()` re-imports the entry for each test, so no test touches the network or leaks state into the next. **The fixture's parity guard:** `tests/stack/wp/quote-page.test.ts` checks that the fixture and the real rendered `/get-a-quote/` form carry exactly the same set of `data-*` hooks, each with its value, so a hook added to or dropped from the template fails there. It compares the hook set, not the nesting: an element moved to another parent still needs a DOM test of its own.

## Tooling and workflow hygiene

Part of the same `pnpm test` run above (`tests/tooling/`, `tests/scripts/`, `tests/workflows.test.ts`), called out separately here because it's a distinct concern: these tests don't exercise application logic, they exercise the tools that keep the committed workflow JSON reviewable and reproducible.

- `tests/tooling/build-workflows.test.ts`, `tests/tooling/check-workflows.test.ts`: the Code-node build and the hygiene checker, each against `tests/fixtures/workflows/` (`clean.json` plus one defect per other fixture).
- `tests/tooling/credentials.test.ts`, `tests/tooling/google-credential-ids.test.ts`: the credential-import plan (skip existing, `--refresh`, blank `.env` values) and the pure `googleCredentialIds()` helper, with no `.env` dependency.
- `tests/tooling/import-workflows.test.ts`: `missingWorkflowIds()`, the pure function behind `pnpm run setup`'s post-import verification: given the manifest's workflow IDs and the set actually seen in n8n, it reports exactly which are still missing, in manifest order.
- `tests/tooling/poll.test.ts`: the bounded execution-lookup poll (`tests/stack/lib/poll.ts`), unit-tested directly against an injected lookup function rather than a live stack, even though its caller (`tests/stack/lib/execution-data.ts`) is a stack-only module.
- `tests/tooling/compose.test.ts`: the merged Compose config mounting `site/theme` read-only as the `chivabox` theme in `wordpress`, `wpcli` and `cron` (through `docker compose config`, so no daemon is needed), and `scripts/lib/compose.ts`'s `compose()` helper, with `node:child_process`'s `spawn` mocked: a successful and a failing exit both resolve/reject with the captured stdout and stderr, a stdin error (e.g. `EPIPE`) rejects instead of throwing, a `spawn` error rejects instead of throwing, and a call with no `input` never spawns at all (it uses `execFile` instead).
- `tests/scripts/check-workflows-cli.test.ts`: the CLI's per-fixture output and exit code.
- `tests/workflows.test.ts`: every committed workflow file's pinned node parameters, IF conditions, Postgres `typeVersion`, retry settings, and `errorWorkflow` wiring, so a hand edit to `workflows/*.json` that drifts from the generated or reviewed form fails here before it fails anywhere live.

**The commands these build and check tools exercise, which CI runs directly (not through a test file):**

- `pnpm run build:workflows -- --check`: fails if a Code node's committed `jsCode` doesn't match a fresh build of its `src/nodes/*.ts` source. Runs in the `quality` job.
- `pnpm run check`: the hygiene checker against `workflows/` itself (pinned data, required settings, no literal secrets, known credential IDs, documented Code nodes, required retries, safe Postgres parameters, a sticky note per workflow). Runs in the `quality` job.

**Staying deterministic and clean:** every hygiene-check case runs against a static fixture file, never the live stack; `tests/fixtures/nodes/double.ts` is a one-line fixture Code-node source shared by the fixtures and tooling tests, so a build test never depends on a real `src/nodes/*.ts` file changing underneath it.

## PHP (PHPCS, PHPStan level 9, PHPUnit)

**Command:** `pnpm run php composer check` (runs `composer lint`, then `composer analyse`, then `composer test`, inside the `php` tools container; there is no local `php` or `composer`). `pnpm run php composer audit` checks dependencies separately.

Never put `--` before `composer`: pnpm 11 passes it through literally, `docker-php-entrypoint` takes it as the command, runs nothing, and exits 0. The container (`profiles: [tools]`, no published ports) runs as the host's own `uid:gid` (`docker compose run --rm --user "$(id -u):$(id -g)" php`) over the read-write `.:/app` mount, so the Composer autoloader and PHPUnit's runtime files aren't written back root-owned on Linux. That uid has no `/etc/passwd` entry, so `compose.yaml` sets `HOME: /tmp` alongside the Dockerfile's `COMPOSER_HOME=/tmp/composer`.

- **`composer lint`**: PHPCS with `WordPress-Extra` plus `PHPCompatibilityWP` (`testVersion` `8.3-`, `minimum_wp_version` `7.0`), over `plugin/moving-quote`, `site/mu-plugins` and `site/theme`, excluding `vendor/`, `assets/`, and both `languages/` folders. `WordPress.WP.I18n` accepts the `moving-quote` and `chivabox` domains, and `WordPress.NamingConventions.PrefixAllGlobals` requires the `chivabox` prefix in the theme only (the plugin is namespaced, and its template's variables are local to `Shortcode::render()`). Two sniffs are excluded with a one-line reason each (`WordPress.Files.FileName` conflicts with PSR-4 file names; `Universal.Arrays.DisallowShortArraySyntax` is dropped because the codebase uses modern `[]` syntax throughout). `WordPress.DB.DirectDatabaseQuery` is excluded only for `src/Leads/LeadRepository.php` and `src/Install/*`, where direct `$wpdb` queries are the point.
- **`composer analyse`**: PHPStan level 9 over `plugin/moving-quote/src`, `moving-quote.php`, `uninstall.php`, `site/mu-plugins`, `site/theme`, and `tests/php`, with `--memory-limit=1G`. Level 9 requires every array touched by a typed helper or data provider to carry an explicit shape (`@param array{…}`).
- **`composer test`**: PHPUnit 11.5, `failOnWarning`, `failOnNotice`, `failOnDeprecation`, and `failOnRisky` all on, over `tests/php/**/*Test.php`, covering every pure class: `Pricing\Calculator` and `Pricing\DistanceTable`, `Settings\SettingsSanitizer`, `Leads\LeadValidator` and `Leads\LeadRecord` (including `is_reference()`, the one gate between the thank-you page's query string and its output), the pure `Delivery` classes (`JwtSigner`, `LeadPayload`, `ResponseCheck`, `Backoff`, `SyncTransition`), the pure `Admin\CsvEscaper` and `Admin\LeadCsv`, `Rest\Responses` (`tests/php/Rest/ResponsesTest.php`: the estimate body's keys, in order), `Leads\EmailRule`, `Rest\LocaleParam` (`tests/php/Rest/LocaleParamTest.php`: only an exact installed locale is accepted from the REST URL's `locale` arg; an uninstalled one, a bare language code, a W3C tag, another case, whitespace, markup, or a non-string is `null`), `Frontend\TranslatedPage` (`tests/php/Frontend/TranslatedPageTest.php`: Polylang's translation replaces the thank-you page only when it's a positive ID; 0, a negative ID, `false`, `null`, or a numeric string keeps the page itself), `Settings\Business` (`tests/php/Settings/BusinessTest.php`: the `+57 000 000 0099` display, the `tel:` and `wa.me` links with an encoded text, and no link at all for a blank number), `Frontend\BusinessSchema` (every city in `areaServed`, the phone, address and hours only when set, no `priceRange`, and a `</script>` in the street kept inside the script element by `JSON_HEX_TAG`), `Frontend\Prefill` (a type or city counts only when it's exactly one the form offers: `<script>`, another case, a city not in the table, a blank, or an array is ignored; and a GET form's target keeps its own query, `?page_id=` or `?lang=`, as hidden fields), `Frontend\RouteChips` (the three default chips' exact "from" prices, a route with no known distance skipped, the shortcode attribute parsed), the business fields in `Settings\SettingsSanitizer` (digits kept from a typed phone, a short one rejected with the old value kept, hours both-or-neither and in order, the length limits), and `Security\RateLimiter::normalize_ip()` (`tests/php/Security/RateLimiterTest.php`): the one pure, WordPress-free piece of that otherwise WordPress-coupled class: an IPv4 address (including an IPv4-mapped IPv6 one) is returned unchanged, and two IPv6 addresses inside the same /64 normalize to the same value while two addresses in different /64s don't. `Delivery\LeadPayloadParityTest` builds the 11 edge-case `LeadRecord`s in `tests/fixtures/lead-payloads/` (range 0 with an unrounded amount, a same-city 0 km move, every extra, the maximum rooms, a tab-normalized name, a 100-code-point name with an emoji, a plus-tagged email, an empty `site_name`, a Spanish `locale`, an empty `locale` from a row saved before that column existed, and a site with no business numbers, whose `contact` is two blanks) and asserts `LeadPayload::body()` matches each fixture byte for byte: the PHP half of the PHP/TS payload parity corpus, proving the committed fixtures are PHP's own real output rather than a hand-written guess for `tests/nodes/lead-payload-parity.test.ts` to check against.

**Staying deterministic and clean:** PHPUnit here never bootstraps WordPress: every class under test lives in `plugin/moving-quote/src/` with no `ABSPATH` guard, specifically so PHPUnit can load it standalone. Every test case is exact (an input and an expected output), not a range check, including the full backoff schedule and every `SyncTransition` state. CI also runs an autoloader-drift check (`composer autoload:plugin`, then `git diff --exit-code -- plugin/moving-quote/vendor`) to catch a PSR-4 mapping change that wasn't followed by a regenerated, committed autoloader.

**Staying deterministic and clean:**

- `tests/stack/global-setup.ts` stops the `cron` sidecar for the whole run, so its background `wp cron event run --due-now` loop can't race a test file's own assertions about exactly which leads were retried when; it restarts the sidecar afterward only if it was running before.
- `tests/stack/lib/stack.ts`'s `sqlWp()` never uses `wp db query`: the `wpcli` image's bundled MariaDB client isn't guaranteed compatible with MySQL 8.4's wire protocol, so it runs `wp eval-file -` instead, executing PHP through WordPress's own `$wpdb`: the same client the plugin itself uses at runtime.
- `tests/stack/lib/leads.ts` tracks every `request_uuid` a test mints and calls `deleteCreatedLeads()` in each file's `afterAll`, since a saved lead is a real delivery attempt and cron keeps retrying a pending one for hours if it's left behind.
- `tests/stack/wp/delivery.test.ts` additionally parks every other pending row (`next_attempt_at` far in the future) before and after each case, and filters its receiver's recorded requests by the body's own `request_uuid` rather than assuming "the last request" is its own: a second layer of defense on top of stopping `cron`, so the file stays correct even under a manual or partial run where that sidecar might still be running.
- `tests/stack/lib/stack.ts`'s `disableDelivery()` patches `webhook_url` to `''` and returns a restore function, for a file whose leads must never actually reach the configured n8n URL.
- `tests/stack/lib/leads.ts`'s `createPendingRowParker()` gives each file its own park/restore pair over other `pending` rows, restoring each row's pre-test `next_attempt_at`, so no row a file doesn't own becomes due mid-assertion.
- `tests/stack/lib/receiver.ts`'s `startReceiver()` stands in for n8n's webhook: it listens on `0.0.0.0` at an ephemeral port, reached at `http://host.docker.internal:<port>/lead`. Every container in `compose.yaml` declares that host through `extra_hosts`, so WordPress, wpcli, and the cron sidecar reach it on Linux CI too.

## The n8n stack suite

**Command:** `pnpm run test:stack:n8n` (`vitest run --config vitest.stack.config.ts tests/stack/n8n`); `pnpm run test:stack` runs it together with the WordPress half. Needs the whole stack (MySQL, WordPress, WP-CLI, Postgres, n8n) healthy, `./setup.sh`, and `pnpm run setup` already run.

Covers the WordPress-to-n8n handoff and n8n's own workflows: `tests/stack/n8n/intake.test.ts` (JWT verification failures, the idempotency gate, concurrent-delivery dedupe, the soft-delete-for-purge check on a successful run), `tests/stack/n8n/process-lead.test.ts` (a read-only decode of a real execution proving "Map lead" ran and the chain reached "Append lead row", and that a Spanish lead's customer email comes out in Spanish inside n8n's own Code-node sandbox: Colombian number grouping and a Spanish date, which depend on that sandbox's own `Intl` locale data), `tests/stack/n8n/error-handler.test.ts` (a signed lead whose `process-lead` run fails at "Append lead row" on the missing credential runs `error-handler`, found by the failed execution's URL in its data: `Compose alert` wrote the English alert to `ops@example.com` naming "Append lead row", and the run reached "Email operator", failing there on the missing Gmail credential), `tests/stack/n8n/end-to-end.test.ts` (a lead sent from the real WordPress path through to n8n, including an n8n-down-then-recovered case and a wrong-secret-then-restored case), and `tests/stack/n8n/runtime.test.ts` (n8n's own health, the Postgres role isolation between the `app` and `n8n` databases, `processed_events` starting empty, and a full run of `node scripts/check-db.ts` against the real stack, printing its output on failure instead of just the bare exit code).

**Staying deterministic and clean:**

- `tests/stack/lib/execution-data.ts` decodes a stored execution's `flatted`-encoded data read-only, through n8n's own bundled `flatted` package inside the container, with its own polling loop (`tests/stack/lib/poll.ts`'s `pollForExecutionId()`) factored out as side-effect-free so it can be unit-tested directly (see "Tooling and workflow hygiene" above) without pulling in the live-stack module.
- `tests/stack/lib/jwt.ts`'s `signHs256()` and `decodeVerified()` sign and verify an HS256 JWT independently with `node:crypto`, and `decodeVerified()` is asserted with `not.toBeNull()` (never by comparing a secret value directly), so a test proves the signature is valid without ever asserting equality on sensitive material.
- **The live-Google skip guard.** Every case that would hand a test lead to `process-lead` checks `googleCredentialsConfigured()` first (`tests/stack/lib/stack.ts`): it lists n8n's credential IDs through a non-decrypted CLI export (the same way `pnpm run setup` itself checks) and skips with a console message once either Google credential already exists. `tests/stack/n8n/end-to-end.test.ts`, `tests/stack/n8n/process-lead.test.ts`, and `tests/stack/n8n/error-handler.test.ts` skip their entire `describe` block this way; `tests/stack/n8n/intake.test.ts` marks only its accepted-lead cases with `it.skipIf(...)`, since its rejection cases and its missing-config case never reach `process-lead` at all. Without this guard, running the suite after the owner wires in the real Google account would append a test row to the real `Moving leads` sheet and email the real team on every run.

## The queue-mode run

**Command:** `docker compose -f compose.yaml -f compose.queue.yaml up -d --wait --scale n8n-worker=2`, then `pnpm exec vitest run --config vitest.stack.config.ts tests/stack/n8n/intake.test.ts` against that stack. Return with `docker compose -f compose.yaml -f compose.queue.yaml down && docker compose up -d --wait`; a plain `down` keeps the volumes.

Not a separate test file: it's the same `tests/stack/n8n/intake.test.ts` suite run against a queue-mode stack instead of the regular single-process one, to prove the JWT check, the raw-body hash, and the idempotency gate all work identically when a worker (not the main process) executes the workflow. The intake suite passes with two workers running, including the five-concurrent-deliveries case giving exactly one `accepted`, and the worker containers' own logs show them starting and finishing the executions. The workers run under the same hardening as `n8n` (`cap_drop: ALL` and `no-new-privileges`), and Redis under `no-new-privileges`.

**Staying deterministic and clean:** `compose.queue.yaml`'s `n8n-worker` service `extends` `compose.yaml`'s own `n8n` service with its published port reset (`ports: !reset []`, so it can scale), so it shares the same encryption key, database settings, and read-only `/files` mounts: nothing queue-specific to keep in sync by hand. The missing-config test case in this suite waits until n8n and every running worker have seen the file change, since in queue mode a worker (not the main process) is what actually executes a waiting run.

**Staying deterministic and clean:** `@wp-playground/cli` is pinned at exactly `3.1.61`, named above, so a version drift in Playground itself can't silently change what this check verifies. Each `server` run starts from a throwaway in-memory virtual filesystem: nothing persists between runs, and nothing written during a manual check needs cleanup. `tests/playground.test.ts` is the one piece of this that runs automatically: it compares `playground/blueprint.json` and `playground/blueprint.local.json` structurally (`steps.slice(2)` deep-equal) so the two blueprints can't drift apart from each other, and checks the English and Spanish blueprints against `setup.sh`'s own copy for each language, without needing the CLI itself. The two public blueprints install from GitHub's `main`, so opening them is one of the README's live checks, run once a release reaches `main`.

## The rule: unit tests never import `.env`-loading modules

`tests/stack/lib/stack.ts` calls `process.loadEnvFile('.env')` at import time. CI's `Quality` job runs `pnpm test` with no `.env` file present at all: only the two stack jobs run `node scripts/init-env.ts` first, so any test file outside `tests/stack/` that imported `stack.ts`, directly or transitively, would throw on import and fail the whole `quality` job.

The rule this repo follows: a helper two or more stack-test files need, with no dependency on the live stack itself, belongs in its own side-effect-free module instead (for example `tests/stack/lib/poll.ts`), so a unit test can import it directly without pulling in `stack.ts`. This rule is also stated in `AGENTS.md`'s "Rules an agent must not break" list.

## The local stack

- **Services and ports.** `db` (MySQL 8.4, unpublished), `wordpress` (`127.0.0.1:8080`), `wpcli` (idle, for one-off `wp` commands), `cron` (`wp cron event run --due-now` every 60 s, since WP-Cron is disabled), `postgres` (unpublished), and `n8n` (`127.0.0.1:5678`).
- **One stack at a time.** Every demo in this series binds `127.0.0.1:5678`, and this one also binds `8080`. Run `docker compose ls` and stop any other demo's stack first, or `up` fails on the port or a test talks to the wrong n8n.
- **`setup.sh`** needs `docker compose up -d --wait` first. It waits until MySQL accepts connections, installs WordPress (admin password over stdin), installs WordPress's `es_CO` core pack, sets the timezone and pretty permalinks, activates the `chivabox` theme (installing its parent, Twenty Twenty-Five, if the image lacks it), installs and activates Polylang at its pinned version, builds the site in both languages (see "Languages and the switcher" in [`i18n.md`](i18n.md#languages-and-the-switcher)), activates the plugin, sets the delivery settings (see "Settings" in [`plugin.md`](plugin.md#settings)), and fills in the demo business details while every business field is still blank. `SITE_LOCALE` picks the default language. It needs network access for Polylang and the language pack.
  - It's idempotent, and leaves an existing page or menu as it is, since the owner may have edited it. The exceptions: a page or menu with no language yet gets its own, a menu without the language switcher gets it appended, and a menu whose switcher shows codes gets the names one. Each page's content is one pattern reference (`<!-- wp:pattern {"slug":"chivabox/home"} /-->`) and its excerpt is the meta description; `SETUP_REFRESH_PAGES=1 ./setup.sh` replaces an existing page's content and excerpt with them, for an older stack.
  - It stops with a message if `wp_navigation` isn't translatable or the `chivabox` theme is missing, which means the containers predate the `site/mu-plugins/` or `site/theme/` mount: run `docker compose up -d --wait` to recreate them.
- **Stack tests never use `wp db query`.** The `wpcli` image's MariaDB client isn't guaranteed compatible with MySQL 8.4; `sqlWp()` runs `wp eval-file -` through WordPress's own `$wpdb` instead.

- `docker compose down`: stop the stack. `-v` also drops the named volumes, wiping WordPress, MySQL, Postgres, and n8n data.

- `pnpm run test:stack`: the full stack suite (`tests/stack/**`). Needs the whole stack healthy and `./setup.sh` run.

- `pnpm run db:migrate`: applies pending `db/migrations/` files, then resets `app_runtime`'s password and attributes. It stops before touching the database on a transaction-control statement, a role-name clash, or an unset `\getenv` variable; a second run prints `no pending migrations`. See `docs/database.md`.

It skips a credential with blank `.env` values, or an existing one unless named with `--refresh <id>` (repeatable): re-importing drops an interactive Google sign-in. (`--refresh cvbCredAppDb0001` is also the one-time move of an existing stack's `App DB` credential onto `app_runtime`; see "Credentials" in `docs/database.md`.) It verifies every manifest workflow id landed (`n8n list:workflow --onlyId`) and retries the import once, since a freshly written file can still be settling onto the bind mount; it fails naming any id still missing.

See `docs/database.md`.
- `pnpm run export`: writes n8n's canonical form of every known workflow back to `workflows/` and regenerates the Code nodes. Run it after editing a workflow in the n8n UI, and commit the result.
- n8n's `import:workflow`, `export:workflow`, `import:credentials`, `export:credentials`, and `publish:workflow` need no owner account, `--userId`, or `--projectId` (checked against `2.45.7`). `publish:workflow` takes effect only after a restart, which `pnpm run setup` does only when it published something (see "Changing a workflow" in [`architecture.md`](architecture.md#changing-a-workflow)).

Open it at `https://playground.wordpress.net/?blueprint-url=https://raw.githubusercontent.com/aabv21/wordpress-moving-quote-plugin/main/playground/blueprint.es.json`.

`tests/playground.test.ts` keeps all three in sync (see "Playground" above).

**The blueprints stay monolingual: no Polylang, no switcher.** Each one shows the plugin in a single language, with the English slugs. A bilingual blueprint would have to repeat, as JSON steps, everything `setup.sh` does through Polylang's PHP API (Polylang free has no WP-CLI commands or blueprint steps): the two languages, the Spanish core pack, ten pages and two menus with their languages and translation links, the tagline's string translation, and the `site/mu-plugins/` filter, which a blueprint would have to fetch and install as a separate step. That copy would drift from `setup.sh`, and the language behavior it would show is the stack suite's to prove. The plugin's own part (the `locale` query arg, the translated thank-you page) is covered by PHPUnit and the stack suite.

**Delivery stays off in Playground**: there's no `.env`, so `setup.sh`'s delivery settings never apply, and a lead shows "Pending (0 attempts)". What was verified there (the mount and `wp-cli` behavior, SQLite compatibility, the lock-value fix, the exact estimate response) is in the "Playground" section above.
