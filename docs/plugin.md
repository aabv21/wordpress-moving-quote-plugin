# The plugin and the site theme

How the WordPress plugin and the demo site's theme work, section by section. The file layout is under "Repository layout" in [`architecture.md`](architecture.md#repository-layout). The rules an agent must not break are in [`AGENTS.md`](../AGENTS.md); the REST and webhook contracts are in [`api.md`](api.md); translations are in [`i18n.md`](i18n.md).

## Install lifecycle

- **Single-site only.** `Installer::activate( bool $network_wide = false )` refuses with `wp_die()` (`back_link: true`) whenever `is_multisite()` is true, per-site activation included. See "Single-site only" in `docs/architecture.md` for the SSRF reason.
- **Activate** creates the leads table through `dbDelta` (`Install\Schema::sql()`), seeds `moving_quote_settings` without overwriting, sets `moving_quote_db_version`, and schedules the outbox hook.
- **Deactivate** only clears the hook; the table and both options stay.
- **Upgrade.** `Installer::maybe_upgrade()` runs on every `plugins_loaded` and reruns `dbDelta` when the stored version differs. `DB_VERSION` is `'2'`, which added `locale` (`varchar(20)`, default `''`). A new column goes last in `Schema::sql()`, since `dbDelta` appends it; an existing row keeps `''`, which n8n reads as the default language.
- **Uninstall** (`uninstall.php`, only when WordPress deletes the plugin) drops the table, both options, the rate-limit transients, and the hook. It's the one path that removes data.
- **Cron.** Hook `moving_quote_process_outbox` on `moving_quote_every_minute` (60 s, added through `cron_schedules`); `Plugin::boot()` wires it to `Delivery\Outbox::process_due()`.

## Settings

- **Admin page.** `Admin\Menu::register()` adds "Moving quotes" (`manage_options`, `dashicons-car`) and its Settings submenu, rendered by `Admin\SettingsPage::render()` in four sections: rates, cities and distances (existing routes, three blank rows, a remove checkbox, and a warning listing any missing city pair), delivery, and business details.
- **Sanitizing a save.** `SettingsPage::sanitize()` uses `esc_url_raw()` for the webhook URL and only `trim()` for the secret and team email, never `sanitize_text_field()` or `sanitize_email()`, which can silently turn a bad value into `''` before validation. The pure `Settings\SettingsSanitizer` then keeps a field's current value and reports an error code on invalid input. `options.php` has already unslashed the value.
- **The webhook secret.** A blank field keeps the stored secret; only a non-blank value (at least 32 characters) replaces it. The field is always `type="password"` with an empty value, so the HTML never contains it.
- **Delivery gating.** `Settings\Options::delivery_enabled()` is true only once the webhook URL, secret, and team email are all set; the page says "Delivery is on" or "Delivery is off until the webhook URL, secret, and team email are set."
- **Business details.** Flat keys, each `''` by default: `business_phone` and `business_whatsapp` (stored as 10 to 15 digits; spaces, `+`, `-` and parentheses are dropped, anything else is `invalid_phone`), `business_street` (≤ 120 characters), `business_city` (≤ 60), `business_tax_id` (≤ 40; a control character is `invalid`, a longer value `too_long`), and `business_hours_open`/`business_hours_close` (`HH:MM`, both or neither, opening first, else `invalid_hours` on `business_hours`). A missing key keeps its current value, so an option saved before the fields existed reads as blank. The pure `Settings\Business` (`Options::business()`) formats them: `phone_display()` (`570000000099` → `+57 000 000 0099`), `tel_href()`, `whatsapp_href( $text )`; each link helper answers `''` for a blank number, so nothing prints a link to nothing.
- **`setup.sh`'s delivery keys.** It sets `webhook_url` to the in-network n8n address, and patches `webhook_secret`/`team_email` from `.env`'s `LEAD_WEBHOOK_SECRET`/`TEAM_EMAIL` with `wp option patch update`, both over STDIN.

## Leads admin

- **The page.** "Moving quotes" and its "Leads" submenu render `Admin\LeadsPage::render()`, which requires `wp-admin/includes/class-wp-list-table.php` (not autoloaded) before using `Admin\LeadsListTable`. Columns: Received (`America/Bogota`), Reference, Customer (name, phone, email), Move (date, type label, "N rooms"), Route (origin → destination, km), Estimate (the REST API's `COP low – high`), Status, and Delivery.
  - Status is a per-row form posting to `admin-post.php`, its `<select>` labelled "Status of lead MQ-…", with a "Delete" link. Delivery shows the sync label, attempts, `last_error` (also in a `title`), and "Retry delivery" on `failed` rows.
  - Each cell has core's markup (`data-colname`; a `<th scope="row">` with "Show more details" for the primary Received column), so narrow screens collapse rows into labelled lines.
  - Views: All plus the five `LeadStatus` values, each with a live count; 20 rows per page; an unknown `status` reads as "All".
  - `single_row_columns()` calls each `column_$name()` directly, and each escapes its own output. Never run that markup through `wp_kses_post()`, which strips the status `<form>`, `<select>`, and `<input>`.
- **The handlers.** `LeadsPage::register_hooks()` wires four `admin_post_moving_quote_*` actions. `admin-post.php` has no capability gate of its own, unlike a menu page, which core's `wp-admin/includes/menu.php` denies with 403 before any callback runs, so each handler checks `manage_options` first, dying with an explicit `403` (`wp_die()` defaults to 500), then `check_admin_referer()`.
  - `handle_update_status()` applies the posted `status` through `LeadRepository::update_status()`; an unknown value is a no-op. It redirects with a notice.
  - `handle_retry()` calls `LeadRepository::requeue()`, which acts only on a `failed` row: back to `pending`, 0 attempts, due now. The notice says "queued for delivery", never "sent": cron delivers.
  - `handle_delete()` calls `LeadRepository::delete()` after `manage_options` (inside `require_id()`) and the row's own `moving_quote_delete_lead_{id}` nonce. The link confirms with `confirm()` first.
  - `handle_export()` sends `nocache_headers()`, `text/csv; charset=utf-8`, and `attachment; filename="moving-leads-{Y-m-d in Bogota}.csv"`, then a UTF-8 BOM, `Admin\LeadCsv::HEADER`, and `LeadRepository::chunk_after()` batches of 500 (an ascending-id cursor, so no row is skipped or re-read) through `fputcsv( $out, $row, ',', '"', '' )`, whose row terminator is `\n`. It `exit`s right after, so nothing can `echo` onto the stream.
- **Styles.** `LeadsPage::enqueue_styles()` loads `assets/admin.css` on `'toplevel_page_' . Menu::SLUG` only: the email (`.moving-quote-leads__email`) and phone stay on one line, the customer column is 16rem wide (core's table is `table-layout: fixed`), and Delete (`.moving-quote-leads__delete`) sits under Update in core's red.
- **CSV safety.** `Admin\CsvEscaper::cell()` (pure) prefixes `'` to a value starting with `=`, `+`, `-`, `@`, tab, or carriage return, the prefixes spreadsheets read as a formula; `null` becomes `''`. `Admin\LeadCsv::row()` (pure) converts `created_at` (UTC) to `received_at` (`Y-m-d H:i`) and keeps every other field raw, not as a label, so the export reads the same in any admin language. Every cell passes through `CsvEscaper`.
- **The stuck-delivery notice.** `Admin\StuckDeliveryNotice` shows a `notice-warning` to `manage_options` users on the Dashboard or the Leads page (`'toplevel_page_' . Menu::SLUG`) when `LeadRepository::count_stuck()` is non-zero: every `failed` lead, plus every `pending` one over an hour old, excluding `won` or `lost`. It links to the Leads page. A second notice shows the rate-limited `submit` count for the current 24-hour window once non-zero.
- **Personal data.** `Admin\PersonalData` registers an exporter and an eraser keyed by email, reached only through core's Tools → Export/Erase Personal Data. Core requires `manage_options` and owns the request (a confirmation email, then the export or erasure), calling both directly rather than through `admin-post.php`, so neither needs its own nonce.
  - `export()` returns every field of every matching lead under `moving-quote-leads`, with display labels for the move type and extras, plus the lead's site language.
  - `erase()` deletes exactly the rows it read, by their UUIDs, in one statement (`LeadRepository::delete_by_uuids()`) and reports `items_removed`. Copies can remain in the sheet, the two sent emails, and for up to 168 h a failed n8n execution, so when it deleted a row it also reports `items_retained => true` and names each `MQ-…` reference (from `uuids_by_email()`, read once) to remove by hand. See retention in `docs/database.md`.

## Delivery

Every saved lead is sent to n8n as a signed request: once right after the insert, then through a cron-driven outbox that retries with backoff.

- **Signing and payload.** `Delivery\JwtSigner::hs256()` signs claims into a compact HS256 JWT (unpadded base64url). `Delivery\LeadPayload::body( $lead, PayloadContext $context, $tz )` builds the exact contract body (`JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE | JSON_THROW_ON_ERROR`; `submitted_at` is `created_at` in `America/Bogota` as `DATE_ATOM`; `locale` is the stored `determine_locale()` value, or `''` for an older row). `Delivery\PayloadContext` carries the site name, the team email, and the business's `contact` numbers (`{"phone":"…","whatsapp":"…"}`, digits or `''`, right after `locale`), which `parseLead()` reads as optional, so a lead queued by an older plugin still parses. `tests/fixtures/lead-payload.json` holds that body for one fixed lead, read by `tests/php/Delivery/LeadPayloadTest.php`. `LeadPayload::claims()` derives `jti` (= `request_uuid`), `iat`, `exp` (`iat + 300`), and `body_sha256` from the built body, so the signature binds the exact bytes sent.
- **Response checks and retries.** `Delivery\ResponseCheck::acknowledged()` alone decides delivery: a 2xx whose JSON `status` is `accepted` or `duplicate`. `Delivery\Backoff::delay_after()` waits `min(60 × 2^(n-1), 21600)` s after the n-th failure, giving up after `MAX_ATTEMPTS` (10). `Delivery\SyncTransition::after_attempt()` turns an outcome into a `Delivery\SyncUpdate` (`sync_status`, attempts, `next_attempt_at`, `last_error` cut to 500 characters with `mb_substr`, `sent_at`), with an exact PHPUnit case for every row of the table.
- **`Delivery\WebhookClient::send()`** is the one caller of `wp_remote_post()`, not `wp_safe_remote_post()`, whose SSRF guard would block the admin-set private Docker hostname. 5 s timeout, no redirects. It returns null on an acknowledged 2xx, or the error text: a `WP_Error` message, `HTTP {code}: {excerpt}`, or `Unexpected response (HTTP {code}): {excerpt}`.
- **`Delivery\Outbox`.** Delivery is at-least-once: n8n dedupes on `jti`, and `apply_sync()`'s `pending` guard keeps a `sent` row `sent`.
  - `deliver( LeadRecord $lead )` builds and signs the request, sends it, and stores the `SyncUpdate` through `LeadRepository::apply_sync()`; it claims nothing.
  - `process_due()` is the cron entry point. It returns 0 without querying when delivery is off; otherwise it loads up to `BATCH_SIZE` (20) rows from `due()`, claims each with a lease counted from that claim (not the batch start), and delivers only what it claimed.
  - A row whose `status` `LeadRecord::from_row()` can't parse (`ValueError`, likely another plugin version) is recorded as a failed attempt from its stored `attempts` and skipped, so the batch continues.
  - **Every internal failure counts as an attempt.** A caught `Throwable` goes through `SyncTransition::after_attempt()` with `last_error` `Internal error: {class}`, never the message (it could carry PII), so a persistent fault backs off to `failed`. It isn't logged separately.
  - **Stale workers are guarded.** `LeadRepository::claim( $id, $expected_next_attempt_at, $lease_until )` updates only on a matching `id`, `next_attempt_at`, and `sync_status = 'pending'`, true only when exactly one row changed; `apply_sync()` writes only while `pending`.
    - NOTE: a runner stalled past its lease can be overtaken, and if the second runner fails and the row returns to `pending`, the first runner's late write can mask that outcome. Upgrade path: fence `apply_sync()` on the lease value `claim()` issued.
  - **`LeadController`'s inline attempt** calls `deliver()` in a try/catch only after a *new* insert and only when delivery is on, with no claim: `insert()` already set `next_attempt_at = now + LEASE_SECONDS`. The response is 201 regardless, though it can wait up to the 5 s timeout.
- **Stack tests.** `startReceiver()` stands in for n8n's webhook, `signHs256()`/`decodeVerified()` sign and verify JWTs (asserted with `not.toBeNull()`, never by comparing a secret), `deleteCreatedLeads()` runs in every lead-creating file's `afterAll`, and `disableDelivery()` keeps a file's leads off the real n8n. `tests/stack/wp/delivery.test.ts` also parks other pending rows and filters requests by `request_uuid`, on top of `global-setup.ts` stopping `cron`. Details in `docs/testing.md`.

## The quote form

- **The other shortcodes**, each registered in `Plugin::boot()`, each enqueuing the form's stylesheet where it renders:
  - `[moving_quote_start quote="get-a-quote"]` (`StartShortcode`): a GET form to the quote page with the move type and both cities as `mq_type`, `mq_from`, `mq_to`. The quote page URL's own query (plain permalinks' `?page_id=`, Polylang's `?lang=`) travels as hidden inputs (`Prefill::form_target()`), since a GET form replaces its action's query. `Frontend\Prefill::from_query()` keeps a value only when it's exactly a move type or one of the cities, so the quote form arrives with them selected and asks for an estimate on load; anything else is ignored, never echoed.
  - `[moving_quote_routes quote="…" routes="A:B,…"]` (`RoutesShortcode`): one chip per route linking to the quote page with both cities, priced by `Frontend\RouteChips` as the low end of a one-room apartment with no extras (`from COP 882,000`); a route with no known distance is left out.
  - `[moving_quote_contact layout="footer|whatsapp|phone"]` (`ContactShortcode`): the business details from Settings as an `<address>` (phone, WhatsApp, street and city, the hours line, the tax ID, then the data policy link), each line only when set, or one WhatsApp or `tel:` link. With every business field blank it prints nothing, not an address holding only the policy link.
  - `[moving_quote_thanks heading="1|0"]` (`ThanksShortcode`): the thank-you card (`heading="0"` drops its "Request received" title for a page whose title says it), with the reference from `ReferenceShortcode`, a `<dl hidden>` that `thank-you.js` fills from the visitor's own `sessionStorage` (`moving-quote:summary`, written by the form just before the redirect, read only for the same reference), and a WhatsApp link whose text carries the reference. It never looks a lead up. `[moving_quote_reference]` stays registered for older pages.
  - `Frontend\SeoHead` prints the `MovingCompany` JSON-LD (`Frontend\BusinessSchema::script()`, encoded with `JSON_HEX_TAG`, pinned by a PHPUnit case with `</script>` in the street) on the front page only, with no `priceRange`, since no single range is honest when the price grows with rooms, distance and extras: name, URL, tagline, language, every route city in `areaServed`, and the phone, address and hours only when set.
- **Shortcodes.** `[moving_quote]` (`Frontend\Shortcode::TAG`) takes one optional attribute, `thank_you` (the redirect page slug, default `thank-you`). With Polylang active, that slug names any page of a translation group, and `thank_you_url()` redirects to its translation in the visitor's language (`pll_get_post()`, behind `function_exists()`, through the pure `Frontend\TranslatedPage::id()`); without it, the slug's own page. `register_assets()` registers the script (footer, `strategy: 'defer'`) and style on `init`, versioned with `Plugin::VERSION`: bump it whenever either changes, or returning visitors keep the cached copy. The plugin's own version moves by the rule in [`CONTRIBUTING.md`](../CONTRIBUTING.md), and always when the script or stylesheet changes. `tests/versions.test.ts` keeps the three equal. `render()` enqueues them, so they load only where used. `[moving_quote_reference]` (`Frontend\ReferenceShortcode`) prints "Your reference number is MQ-…" from the `reference` query arg only when `LeadRecord::is_reference()` matches (`MQ-` and 8 uppercase hex digits), and never looks it up, so the page can't probe which leads exist.
- **Markup** (`templates/quote-form.php`). A `<form data-moving-quote data-config="…">` with a numbered progress `<ol role="list">` (markers `aria-hidden`, `aria-current="step"` on the current one), three `<fieldset>`s, a `role="alert"` error region, a hidden inline success message, the estimate panel, a honeypot, and a `<noscript>` fallback.
  - The form's main column and an `<aside class="moving-quote__summary" data-summary>` share a grid: the summary holds `[data-summary-route]`, `[data-summary-date]`, `[data-summary-extras]` (each starting with the server's translated placeholder, marked `data-empty` and styled as a muted hint until its field is filled; the date shows in the page's language, `15/12/2026` in Spanish), the estimate block, and, with a business phone, a call line. Each extra shows its price (`Messages::added_price()`), a note under the progress list says which fields are required, and the phone field is described by its example and its error.
  - The honeypot (`name="website"`) sits in an off-screen, `aria-hidden="true"` wrapper out of the Tab order (`tabindex="-1"`).
  - Move type, rooms (1–5, "5+"), and both city selects render server-side from `Pricing\MoveType` and `DistanceTable::cities()`; each city select starts with a disabled "Choose a city". Name, phone, and email carry `autocomplete`.
  - `data-config` is `wp_json_encode()` through `esc_attr()`, so no merchant-editable string can break out of the attribute.
- **The markup contract.** `quote-form.ts` and its `form/` modules find everything through hooks, never layout: `[data-summary]`, `[data-summary-route]`, `[data-summary-date]`, `[data-summary-extras]`, `[data-step]`, `[data-progress-step]`, `[data-next]`/`[data-back]`/`[data-submit]`, `[data-error-for="<field>"]` (each the `aria-describedby` target `mq-error-<field>`), `[data-form-error]`, `[data-success]` with `[data-success-reference]`/`[data-success-reference-value]`, and `.moving-quote__estimate` with `[data-estimate-result]`, `[data-estimate-value]`, `[data-estimate-error]`, and `[data-estimate-hint]`. Rename one only together with `quote-form.ts`.
- **Frontend behavior** (`src/frontend/`).
  - One browser-minted UUID v4 `submission_id` per page load, reused on every retry.
  - Estimates run through `debounce(createEstimateFetcher(...), 300)`. `createEstimateFetcher()` wraps only `postJson()` in `latestOnly()` and writes the display itself when the result `!== undefined`, because `latestOnly()` discards a superseded return value, not side effects.
  - A form rendered with every pricing field already chosen (a prefilled link) asks for one estimate on load.
  - The panel's `data-estimate-state` is `idle` (an empty value, with a hint), `loading` (`aria-busy="true"`, so the live region announces only the final price), `ready`, or `error` (the dash plus a message that the request can still be sent).
  - Changing steps focuses the new `<legend>`; Enter before the last step means "Next".
  - Submit disables the button and shows "Sending…". A 2xx with a reference saves the summary's route and date, and the price from the response's own `estimate.display` (the panel's when the response has none), in `sessionStorage` (a storage that throws just loses it), then redirects to the thank-you page with `?reference=MQ-…`, or, with no such page, shows the inline success and focuses it. A 422 returns to the first step with an error and focuses its first invalid control. A 403 (either nonce code), a 429, or a network failure shows its message and re-enables the button; any other non-2xx, a 500 or a 404 say, shows "Something went wrong on our side" instead of the connection message. Only a genuine 2xx shows success or leaves the button disabled.
- **Styles** (`assets/quote-form.css`). Every color, radius, and spacing value is a `--mq-*` token on each block's root class, each with a literal default (`--mq-color-accent: #1d4ed8`), and the stylesheet never reads a theme preset (`tests/plugin-styles.test.ts` keeps `--wp--preset` out): a theme's slugs such as `contrast` or `base` mean other colors in other themes (Twenty Twenty-Five's dark "Evening" variation makes `contrast` near-white), which would turn the form's text white on its own white surface. A theme that wants the blocks in its palette sets the tokens itself, as the Chivabox theme's `style.css` does. The form draws its own light surfaces (`color-scheme: light`); "The design tokens" in `docs/architecture.md` lists each pair's WCAG ratio. Every action is the near-black pill; Back is the outlined pill. At 48rem of form width the summary sits beside the form, sticky; below that it becomes a price bar pinned to the bottom of the screen once a price exists, and `scroll-padding-bottom` keeps a focused field clear of it. A step change fades in over 150 ms (none under reduced motion). Type inherits family and weight, with size clamped to `1rem`–`1.25rem`. A container query on the form itself, not the viewport, switches one column to two, so it also fits a narrow sidebar on a wide screen. Controls are at least 44 px tall; only `:focus-visible` draws the ring; motion is 150 ms on color, opacity, or transform, and `prefers-reduced-motion` drops it (spinners pulse instead of turning).
- **The generated assets.** `quote-form.js` and `thank-you.js` are built by `pnpm run build:assets` (one esbuild entry each, `ENTRIES` in `scripts/build-assets.ts`) and committed; never edit them by hand.
- **Field messages.** `Rest\Messages::fields()` maps error codes to text for both endpoints. Phone and email name a valid value ("Enter a phone number with 10 to 15 digits.", from `LeadValidator::PHONE_MIN_LEN`/`PHONE_MAX_LEN`; "Enter an email address like name@example.com."); the name and date messages name their own limits too (`NAME_MIN_LEN`, `NAME_MAX_LEN`, `MOVE_DATE_MAX_DAYS_AHEAD`, all public constants); other fields share the generic text.

## The site theme

`site/theme/` is the demo site's block theme, `chivabox`, a child of Twenty Twenty-Five, mounted read-only like `site/mu-plugins/`. It is the site, not the plugin: the plugin works under any theme.

- **What lives where.** The plugin owns what only it knows: the business details, the route prices, the quote form, the thank-you card, and the home page's JSON-LD. The theme owns the look (`theme.json`'s palette, fonts, sizes and button; `style.css`'s layout, and the plugin's `--mq-*` tokens pointed at its presets), the page copy (`patterns/`), the templates (`front-page.html` has no post title; `page.html` puts the title and the content on one left edge, text at 65ch), and the meta tags.
- **Patterns, not stored copy.** Each page's content is one `<!-- wp:pattern {"slug":"chivabox/…"} /-->`, so the copy translates through gettext and changes with the theme. Header and footer parts are pattern references too, so their strings translate. Links use `chivabox_page_url()`. A template part never passes through `the_content`, so a shortcode block there would print its own text: the header and footer patterns print the plugin's shortcodes with `chivabox_shortcode()` (`do_shortcode()`, and nothing when the plugin is inactive). The stylesheet's version is its own modification time, so a changed `style.css` is never served from a cache.
- **Meta tags.** `chivabox_head_tags()` (`wp_head`, priority 1) preloads the two above-the-fold fonts, sets `theme-color`, links `assets/images/icon.svg` when no site icon is set, and, on singular pages, prints the meta description (the page's excerpt, else the tagline), Open Graph (`og:url` from `wp_get_canonical_url()`, `og:image` `assets/images/og-default.jpg` at 1200 × 630, `og:locale` from `determine_locale()`) and `twitter:card`, every value through `esc_attr()`.
- **Assets.** The fonts are self-hosted woff2 (`font-display: swap`), never Google Fonts. The photos are Unsplash (Unsplash License), with no readable brand, logo, or close-up face, each credited in `site/theme/CREDITS.md` with its edits. Keep each photo within its size budget (hero ≤ 220 KB, the 800 px copy ≤ 90 KB, the services photo ≤ 140 KB, the Open Graph image ≤ 200 KB).
