# How Chivabox Movers works

This page follows one lead from the quote form to the team's inbox. It then covers the data model, failure modes, scaling limits, security, and the design choices behind each part.

## Context: who uses it and where it runs

Chivabox Movers is a fictional moving company on Colombia's Caribbean coast. Its WordPress site embeds a `[moving_quote]` shortcode: a three-step form that prices a move in Colombian pesos (COP) from a move type, room count, origin and destination city, and optional extras, then saves the request as a lead.

The repo holds two parts:

- **The WordPress plugin** (`plugin/moving-quote/`): a pure pricing engine, the leads table and its REST API, the admin settings and leads pages, and signed delivery to n8n with a cron-driven retry outbox.
- **The n8n backend** (`workflows/`): three workflows that verify each signed lead, record it once, write it to a Google Sheet, and email the team and the customer.

The whole stack runs as one Docker Compose project, `chivabox-movers`:

- **WordPress 7.1.4** on PHP 8.3, published on `127.0.0.1:8080`, backed by MySQL 8.4 (unpublished), with Polylang 3.9.1 making the demo site bilingual (English at `/`, Spanish under `/es/` by default)
- **A WP-CLI sidecar** (`cron`) that runs `wp cron event run --due-now` every 60 seconds, since WP-Cron itself is disabled in the container
- **n8n**, on the 2.45 line, published on `127.0.0.1:5678`, backed by Postgres 17 (unpublished)
- **Redis and `n8n-worker`** (optional, `compose.queue.yaml`): queue mode, covered under Scaling

WordPress reaches n8n only over the Compose network, at `http://n8n:5678`; nothing outside the stack calls n8n. The backend calls two external services under one Google account: Google Sheets and Gmail.

## How a lead moves from the form to the inbox

The sequence diagram groups the path into six segments. Open the [interactive page](diagrams/lead-sequence.html) to read it full-size.

![Lead delivery sequence: estimate, submit and insert, signed POST and verify, record and respond, hand off to process-lead, and an alternative retry loop when delivery first fails](diagrams/lead-sequence.svg)

Three things the diagram's boxes and arrows can't show on their own:

- **The insert sets a lease, not just a row.** `insert()` writes `next_attempt_at = now + LEASE_SECONDS` (120 s) before the inline delivery attempt runs, so no cron pass can claim that same row as due until the lease expires — see "Concurrent inline and cron sends" below.
- **WordPress prices the move itself.** `LeadController` ignores any `amount`/`low`/`high` the client sent and recomputes the estimate from the current settings before saving, so a tampered client-side price never reaches the stored lead or the sheet.
- **The 5-second ceiling is a blocking one.** The inline delivery attempt runs synchronously inside the same request that answers the browser, so a slow (not just a failed) n8n response can delay the customer's `201` by up to `WebhookClient`'s 5-second timeout before WordPress gives up and answers anyway.

## The workflows, node by node

### lead-intake

`workflows/lead-intake.json` (`cvbLeadIntake001`) receives the signed handoff from WordPress:

1. **Receive lead** (Webhook v2.2). `POST moving-quote/leads`, `authentication: jwtAuth` against the `Lead webhook JWT` credential (`cvbCredLeadJwt01`), `responseMode: responseNode`, and `options.rawBody: true`, so the exact bytes land in binary `data` for hashing. The native check verifies the signature with `jsonwebtoken`, and `exp` only when present. It rejects a missing token (plain-text 401), or a bad signature, an expired token, or `alg: "none"` (plain-text 403), before any execution starts, so none of those reaches Postgres or raises a workflow error. A signed token with no `exp` passes and is rejected next as `missing_claims`.
2. **Hash raw body** (Crypto v2). Lowercase hex SHA-256 of binary `data` into `body_sha256`: the same bytes and algorithm as `Delivery\LeadPayload::claims()`.
3. **Verify request** (Code, from `src/nodes/verify-request.ts`). One tested function, instead of a chain of IF nodes, checks in order: the four claims and their types (`missing_claims`), a lifetime of at most 300 s (`token_lifetime`), `iat` at most 60 s ahead (`token_not_yet_valid`), `exp` not passed (`token_expired`), the body hash (`body_hash_mismatch`), the contract (422 `invalid_payload`), and `jti` = `request_uuid` (`jti_mismatch`). `parseLead()` checks `move.date` only as a calendar date: the today-to-365-days window is WordPress's submit rule, and re-checking it would reject a legitimate retry once the window moves.
4. **Request valid?** (IF on `{{ $json.ok }}`). False goes to **Reject request**, which answers `{ status: 'rejected', reason }` with the 401/422 `Verify request` returned as the HTTP code.
5. **Read config** → **Parse config** (Read/Write Files v1.1, then Extract From File `fromJson`). A `fileSelector` with no match throws `No file(s)…` (verified against the instance's stored error runs), failing the run with a loud 5xx before **Record request**. `alwaysOutputData: true` and `executeOnce: true` stay pinned on **Read config** in case a future n8n returns zero items instead.
6. **Record request** (Postgres v2.8, `App DB` / `cvbCredAppDb0001`, retry 3× at 1,000 ms). `INSERT INTO processed_events (source, event_id) VALUES ('wordpress-lead', $1) ON CONFLICT DO NOTHING RETURNING event_id`, with `$1` bound through `options.queryReplacement` to the verified `request_uuid`. On a replay the node (v2.3+) synthesizes `{ success: true }` with no `event_id`; `alwaysOutputData: true` lets that item reach the gate.
7. **New request?** (IF: `{{ $json.event_id }}` exists). True answers **Respond accepted** (200 `{"status":"accepted"}`), false **Respond duplicate** (200 `{"status":"duplicate"}`); `Delivery\ResponseCheck::acknowledged()` treats both as delivered.
8. **Prepare lead** (Edit Fields) → **Process lead** (Execute Workflow `cvbProcessLead01`, `mode: 'each'`, `options.waitForSubWorkflow: false`), after **Respond accepted** only: a replay was already processed on its first delivery.

**Postgres is pinned at 2.8.** The n8n 2.45 line runs Postgres node v2.8 (checked against 2.45.7 by publishing and exporting this workflow unchanged). The n8n-mcp validator's bundled node data is behind and reports `typeVersion 2.8 exceeds maximum supported version 2.7`; that's stale tool data, not an error. `tests/workflows.test.ts` pins every Postgres node at 2.8, so a downgrade to silence the validator fails.

**Anchoring.** Every cross-node reference uses `.first()` (e.g. `$('Verify request').first().json.lead.request_uuid`), never `.item`, whose pairing through a Code node isn't guaranteed. NOTE: one webhook call carries exactly one lead, so `.first()` is always right; a workflow that batched leads would need a different anchor.

### process-lead

`workflows/process-lead.json` (`cvbProcessLead01`) is entered only through `lead-intake`'s fire-and-forget handoff, with `{ lead, config }`:

1. **When called** (Execute Workflow Trigger, `inputSource: 'passthrough'`): no declared schema to drift from its one caller.
2. **Map lead** (Code, from `src/nodes/map-lead.ts`). One tested function builds, in one pass:
   - `row`, keys in `SHEET_HEADERS` order, ending with the lead's `request_uuid`. `received_at` is `submitted_at` in `America/Bogota`, `yyyy-LL-dd HH:mm`; `move_type` and `extras` (joined with `, `) use English labels whatever the email language, so the sheet stays one dataset; every other value, `phone` and a formula-looking `name` included, passes through unchanged.
   - `team`: `{ to, subject, text }`, plain text in the config's `team_locale`, or English with a last-line note when that value is invalid.
   - `customer`: `{ to, reply_to, subject, html }`, escaped HTML in the lead's own language. `escapeHtml()` covers `& < > " '`.
   - All copy lives in one `{ en, es }` `MESSAGES` table (labels, move types, extras, room plurals, the long date through Luxon `setLocale`, COP grouping through `Intl.NumberFormat` `en-US`/`es-CO`); `run()` escapes or `oneLine()`s every value before a message function sees it.
3. **Row fields** (Edit Fields, `jsonOutput: '={{ $json.row }}'`).
4. **Append lead row** (Google Sheets, `cvbCredGSheets01`, retry 3× at 1,000 ms). `appendOrUpdate` matched on `request_uuid` (`columns.matchingColumns: ['request_uuid']`), with `documentId`/`sheetName` from `config.google.leads_sheet_id`/`leads_tab` (`sheetName` in `name` mode, which matches by title only), `autoMapInputData`, and `options.cellFormat: 'RAW'`, so `570000000001` stays text, not `5.7E+11`, and a formula-looking name never runs. A retry after the row already landed (n8n's own 3 tries after a lost acknowledgement, or an operator's retry) updates that row instead of adding a second. The key is the full `request_uuid`, unique in the leads table, never `reference`: that's only its first 8 hex digits, and the visitor's browser chooses the UUID, so a crafted lead could share another lead's reference and overwrite its row. `options.handlingExtraData: 'error'` overrides n8n's default, `insertInNewColumn` (checked against 2.45.7), which would silently add a column for a renamed header instead of failing and alerting.
   - NOTE: each run reads the `request_uuid` column to find a match, which is fine for tens of thousands of rows. The upgrade path is checking a keyed store before writing.
5. **Email team** (`emailType: 'text'`) and **Email customer** (`emailType: 'html'`, `options.replyTo` set to the team's address), both Gmail with `cvbCredGmail0001`, retry 3× at 1,000 ms, wired from **Append lead row** and reading `$('Map lead').first().json`. Both set `options.appendAttribution: false`. Neither sets `options.senderName`: it calls `GET users/me/profile` first (checked against 2.45.7), which `gmail.send` doesn't authorize, so the display name comes from the Google account's "Send mail as" setting.

**Why Email team is plain text.** `LeadValidator::validate_email()` and `src/nodes/lead.ts` share one rule (see "Output safety" below), but it still allows `?`, `&`, and `=` in the local part, so a crafted address like `victim@example.com?body=...` could pre-fill a `mailto:` reply. The team alert, built from untrusted fields, therefore carries no `tel:` or `mailto:` links; Gmail still links a recognizable phone or address on its own. The customer email stays HTML: its formatting matters more, and it goes to the submitter's own address.

### error-handler

`workflows/error-handler.json` (`cvbErrorHandler1`) is every other workflow's `settings.errorWorkflow`. It reads config through its own nodes, never a sub-workflow (unlike demo 3's `load-config`): a sub-workflow would need its own `errorWorkflow`, and naming this handler would alert on the alert's own failure. With none, a missing or unparseable `config/config.json` fails it once and stops.

1. **On workflow error** (Error Trigger). Also fires on a trigger or activation failure (e.g. a revoked credential at startup), whose payload has no `execution` key, only `trigger`.
2. **Read config** → **Parse config**, the same pair and pins as `lead-intake`'s.
3. **Alert input** (Edit Fields, raw mode). Hands the next node `{ config, failure, time }`: the parsed config, the Error Trigger's own output (`$('On workflow error').first().json`, since `$json` here is `{ config }`), and the time in `America/Bogota` as `yyyy-LL-dd HH:mm`. The clock stays here, so the Code node after it is pure.
4. **Compose alert** (Code, from `src/nodes/error-alert.ts`). One tested function picks the language from `team_locale` through `teamLocaleOrDefault()`, the same never-throwing reader `map-lead` uses, and builds `{ to, subject, text }` from either payload shape. It never throws: a throw here would silence every alert. `oneLine()` keeps a line break in the workflow name out of the subject.
5. **Email operator** (Gmail, `cvbCredGmail0001`, retry 3× at 1,000 ms, `emailType: 'text'`, `appendAttribution: false`), sending `$json.to`, `$json.subject`, and `$json.text`.

The alert's copy, from `error-alert.ts`'s `ALERT_MESSAGES`:

| Part | `en` | `es` |
|---|---|---|
| Subject | `[Chivabox demo] Workflow failed: {name}` | `[Chivabox demo] Falló el flujo: {name}` |
| Lines | `Failed node: …`, `Error: …`, `Execution: …`, `Time: {time} America/Bogota` | `Nodo que falló: …`, `Error: …`, `Ejecución: …`, `Hora: {time} America/Bogota` |
| Fallbacks, for a trigger failure or an empty payload | `unknown workflow`, `activation`, `unknown error`, `n/a (activation error)` | `flujo desconocido`, `activación`, `error desconocido`, `no aplica (error de activación)` |

An invalid `team_locale` gives the English alert with the same last-line note the team email gets.

### Publishing and versions (checked against 2.45.7 on 2026-11-11)

- **A workflow publishes before its credentials exist.** `process-lead.json` imported and published (`publish:workflow --id=cvbProcessLead01`) cleanly and came up `active: true` with neither Google credential present (confirmed from a non-decrypted `export:credentials`). Existence is checked only at execution time: "Append lead row" then fails with `Credential with ID "cvbCredGSheets01" does not exist for type "googleSheetsOAuth2Api."`.
- **A production run uses the published version, parent and sub-workflow alike.** Verified by publishing `cvbProcessLead01` at an older `--versionId` while a newer draft was the current version, then sending a signed lead through the live webhook: the `process-lead` execution's `execution_entity.workflowVersionId` recorded the published id, and the same held for `lead-intake`. Manual or chat-triggered runs aren't covered: n8n's `isManualOrChatExecution` branch (`workflow-execute-additional-data.js`) loads the draft for that mode, and this repo never runs one in production.

## Data model

| Store | What it holds |
|---|---|
| **The leads table** (`{$wpdb->prefix}moving_quote_leads`, MySQL) | One row per `request_uuid` (unique key): the move's fields, the computed estimate, the lifecycle `status` (`new`/`contacted`/`quoted`/`won`/`lost`), the delivery state (`sync_status`, `attempts`, `next_attempt_at`, `last_error`, `sent_at`), and the `locale` the lead was submitted under (the quote page's language, from the REST URL's `locale` arg, else `determine_locale()`; `''` on a row saved before schema version 2), which n8n uses to pick the customer email's language. Indexed on `(status, created_at)` for the admin list and `(sync_status, next_attempt_at)` for the outbox's due-row query. |
| **`processed_events`** (Postgres, database `app`) | `(source, event_id)` as the primary key, `received_at` as a timestamp. `lead-intake`'s idempotency gate: `source` is always `'wordpress-lead'`, `event_id` is the lead's `request_uuid`. |
| **The settings option** (`moving_quote_settings`, autoloaded) | One array: base rates, per-room and per-km prices, extras prices, the range percentage, the routes list, and the three delivery fields (`webhook_url`, `webhook_secret`, `team_email`), each `''` until the owner sets it. |
| **The sheet** (`Moving leads` tab, external) | One row per `request_uuid`: 16 columns in a fixed header order (`SHEET_HEADERS`), the last being `request_uuid`, the key a retried run matches on. Written in `RAW` cell format, so a phone number or a formula-looking name is stored exactly as sent. |

## Failure modes

Unless a row says otherwise, every Postgres, Google Sheets, and Gmail node retries 3 times, 1,000 ms apart. A failure that outlasts its retries fails the execution, and `error-handler` emails the operator. Delivery backs off `60 × 2^(attempts-1)` seconds after each failed attempt, doubling up to a 6-hour cap, and gives up after 10 attempts — about 8.5 hours after the first failure (`SyncTransition.php:21-22`). A `failed` lead only moves again when an admin clicks "Retry delivery" (`LeadRepository::requeue()`), which resets it to `pending` with 0 attempts, due immediately.

| Failure | Behavior | Detection | Recovery |
|---|---|---|---|
| Polylang is deactivated or missing | The plugin keeps working in the site language (`WPLANG`): the form, its REST answers, and the stored `locale` all follow it, and the thank-you redirect goes to the slug's own page. The `/es/` URLs and the switcher are gone, and both header menus compete, so the newest (Spanish) one shows for everyone. | `/es/` answering 404, or a Spanish header menu on English pages | Rerun `./setup.sh`, which installs and activates the pinned Polylang. |
| The containers predate the `site/mu-plugins/` mount | `setup.sh` stops before touching any page: without the mu-plugin, Polylang can't give a menu a language, and every visitor would get the newest menu. | `setup.sh: the header menus can't be translated` | `docker compose up -d --wait` recreates the WordPress containers with the mount; then rerun `./setup.sh`. |
| The plugin is updated before the workflows | A `lead-intake` published before the payload's `locale` field rejects every lead that carries it with 422 `invalid_payload` (its contract allows no extra key). WordPress backs each one off and retries it until it gives up as `failed`. | The admin's Delivery column (`HTTP 422`), or the stuck-delivery notice | Publish the workflows first (`pnpm run setup`), then update the plugin. Leads already `failed` this way go back through "Retry delivery" once the new workflows are published. |
| `config.json`'s `team_locale` is neither `en` nor `es` | Neither `map-lead` nor `error-handler`'s `Compose alert` fails on it: the team email and the operator alert fall back to English with a last line naming the problem, and the customer email still goes out in the lead's own language. | That line in every team email and alert | Set `team_locale` to `en` or `es` in `config/config.json`; the next lead picks it up. |
| n8n is down when WordPress delivers | `WebhookClient::send()`'s `wp_remote_post()` fails with a transport error. The lead stays `pending`, backed off per `Backoff::delay_after()`. | The admin's Delivery column, or the stuck-delivery notice | Bring n8n back up. The outbox's cron-driven retry (the sidecar's 60 s loop) resends the same signed lead once its backoff elapses; n8n dedupes on `jti`. If backoff has already pushed the lead to `failed`, use "Retry delivery" instead of waiting. |
| n8n is slow (past the 5 s timeout) | `WebhookClient`'s 5 s timeout fires before n8n answers. WordPress records the timeout as `last_error` and backs off, but the request may still complete on n8n's side — so the retry's own signed POST reaches `lead-intake` as a second, otherwise-identical request for the same `jti`, which n8n answers `duplicate`. | Nothing distinguishes this from an ordinary retry after the fact: a successful attempt clears `last_error` to `''` (`SyncTransition.php:16`), and WordPress keeps no history of which answer (`accepted` or `duplicate`) a past attempt got. The only trace is a lead that ends `sent` with 2 or more attempts. | None needed: `jti` dedupe means the retry never double-records the request, even though it reached n8n twice. |
| A wrong or rotated webhook secret | Every signed request fails `lead-intake`'s Webhook node's own `jwtAuth` check (plain-text 403, bad signature) before any execution starts. WordPress sees a non-2xx and backs off; no execution and no alert. | n8n's executions list shows nothing for the window, while the admin's Delivery column shows growing attempts, eventually `failed`. | Put the current secret in both places that must agree: `LEAD_WEBHOOK_SECRET` plus the `Lead webhook JWT` credential (`pnpm run setup -- --refresh cvbCredLeadJwt01`) if n8n holds the stale one, or the Settings page's webhook secret field if WordPress does. Then use "Retry delivery" on any lead already `failed`, or wait for the next outbox pass on one still `pending`. |
| A double submit (the same browser tab, two clicks) | The frontend reuses one browser-minted `submission_id` for every attempt from the same page load (`quote-form.ts:60`). A back-to-back resubmission of an already-saved `submission_id` returns through `find_by_uuid()` with no new insert (`LeadController.php:82-85`); a genuine race between two near-simultaneous requests is resolved by `LeadRepository::insert()`'s unique-key race, where the losing request looks up and returns the winner's own row. Only the winning insert triggers delivery. | Exactly one row for the pair, visible in the admin as one lead with one `attempts` count. | None needed. |
| Concurrent inline and cron sends | `insert()` sets `next_attempt_at = now + LEASE_SECONDS` before the inline attempt runs, so no cron pass can see that same row as due until the lease (120 s) expires. | — | None needed. |
| Postgres is down | Verified live (`docker compose stop postgres`, then a signed lead through the real REST API): n8n's own database connection drops (`TypeORMError: Driver not Connected` in its logs, from a background workflow-publication task), but the `n8n` container itself stays healthy and `/healthz` still answers 200. The webhook call never reaches a workflow execution: n8n's own middleware answers the POST with `503 {"code":503,"message":"Database is not ready!"}` before any node runs. ### Recovering a false duplicate

"Record request" keeps its retries: without them a genuine transient failure would drop a lead for good, which is the far more common case. When a lead is in `processed_events` but missing from the `Moving leads` sheet (found by comparing a WordPress lead's `request_uuid` against both):

1. Delete its `processed_events` row (`event_id` = the lead's `request_uuid`). The outer double quotes pass one argument to `sh -c`, and `\$APP_DB_USER` expands in the container's shell, not the host's:

   ```sh
   docker compose exec -T postgres sh -c "psql -U \"\$APP_DB_USER\" -d app -c \"DELETE FROM processed_events WHERE event_id = '<request_uuid>'\""
   ```

2. Set the WordPress row back to `pending` and due. The stack can't use `wp db query` (the `wpcli` image's MariaDB client isn't guaranteed compatible with MySQL 8.4), so this runs through `wp eval` and WordPress's own `$wpdb`:

   ```sh
   docker compose exec -T wpcli wp eval 'global $wpdb; $wpdb->update($wpdb->prefix."moving_quote_leads", ["sync_status" => "pending", "next_attempt_at" => 0], ["request_uuid" => "<request_uuid>"]);'
   ```

3. Run the outbox cron (`wp cron event run moving_quote_process_outbox`, or wait for the sidecar's 60 s loop). WordPress resends the identical signed lead; with the row gone it reaches `Respond accepted`, and the handoff to `process-lead` runs.

## Scaling

- **Outbox batch and real cron.** `Outbox::process_due()` claims up to `BATCH_SIZE` (20) due rows per pass. The cron sidecar runs every 60 seconds; a real deployment points system cron at the same `wp cron event run` command instead of a container loop. The consequence of the batch size: the outbox can drain a backlog of failed leads at most 20 a minute, so a long outage followed by recovery takes proportionally longer to clear than it took to build up.
- **Queue mode.** `compose.queue.yaml` adds Redis and `n8n-worker` containers, which run executions instead of the main process. `docker compose -f compose.yaml -f compose.queue.yaml up -d --wait --scale n8n-worker=2` brought Redis, n8n, and two workers up healthy, with the intake suite passing 13/13 against them, including the five-concurrent-deliveries case giving exactly one `accepted`. Rechecked on 2026-11-11 with `n8n` and both workers under `cap_drop: ALL` and `no-new-privileges`, and Redis under `no-new-privileges`: the same 13/13. The override gives Redis no password; set `QUEUE_BULL_REDIS_PASSWORD` before production use.
- **The Sheets write quota.** Google's documented limits: 60 read requests and 60 write requests per minute per user per project, and 300 of each per minute per project ([Sheets API usage limits](https://developers.google.com/workspace/sheets/api/limits), checked 2026-11-02). "Append lead row" makes one write per accepted lead, so a single demo account tops out near 60 leads a minute on that quota before Google answers 429, which the node's 3 retries 1,000 ms apart can't outlast.
- **Gmail sending limits.** The demo uses a personal Gmail account, not a Google Workspace account; Workspace accounts have different limits ([Gmail sending limits](https://support.google.com/mail/answer/22839), checked 2026-11-02). For a personal account, the page documents two separate thresholds that trigger "You have reached a limit for sending mail": "a total of more than 500 recipients in a single email," and, separately, "more than 500 emails sent in a day" — after either, sending typically resumes within 1 to 24 hours. Every email here has exactly one recipient, so the per-email recipient limit never applies; the one that binds is the daily-count limit. Each accepted lead sends 2 emails (team, customer), so that limit caps the account near 250 leads a day.

## Security

- **Delivery.** JWT HS256, with the algorithm pinned by the `jwtAuth` credential (not read from the token's own header), a 300-second lifetime, and a `body_sha256` claim binding the signature to the exact bytes sent. `jti` (= `request_uuid`) is the one mechanism that both dedupes a replay in n8n and serves as the idempotency key in `processed_events` — the two are the same check, not two separate ones. **The webhook URL must be `https://` the moment it leaves the private Compose network.** `setup.sh` points it at `http://n8n:5678` only because that address never leaves the Compose network's own internal DNS; `WebhookClient::send()` calls `wp_remote_post()`, not `wp_safe_remote_post()`, specifically so the admin can point it at a private hostname the safe variant's SSRF guard would otherwise block (see "Delivery" in `AGENTS.md`) — but that same lack of a safe-URL guard means nothing in this plugin stops an admin from pointing it at a plain `http://` address once n8n sits anywhere reachable off that network. The JWT and the lead's own personal data (name, phone, email, move details) travel in the request body and the `Authorization` header; over plain HTTP past the Compose network, both are readable to anything on the path. A production deployment that doesn't keep n8n on the same private network as WordPress must use `https://` for the webhook URL.
- **Secret storage.** The webhook secret lives in `.env` (`LEAD_WEBHOOK_SECRET`, gitignored) and the WordPress `moving_quote_settings` option today. NOTE: a production deployment should move it to a `wp-config.php` constant instead (e.g. `define( 'MOVING_QUOTE_WEBHOOK_SECRET', '…' )`, read in place of the option field), so the secret never sits in the database at all — the upgrade path this demo doesn't take.
- **Request checks.** Every visitor's `POST /leads` request is checked against the REST `wp_rest` nonce (`X-WP-Nonce`), every admin handler checks `manage_options` before its own nonce, every hand-written SQL query goes through `$wpdb->prepare()` with `%i` for the table name (the install schema uses `dbDelta`, and a few lifecycle writes use `$wpdb->insert()`/`$wpdb->update()` instead, which escape their values without a separate `prepare()` call), a honeypot field (`website`) catches a bot that fills every field by DOM access, and a fixed-window rate limit (120/600 s for estimates, 5/3,600 s for submissions by default, both filterable through `moving_quote_rate_limits`) is keyed on a hashed client IP under a MySQL named lock, so a concurrent burst can't all read the same stale count — per IPv4 address or IPv6 /64, since `RateLimiter::normalize_ip()` zeroes the last 64 bits of any IPv6 address before it's hashed, so every address inside one visitor's /64 shares one budget instead of each one minting its own. The normalization is part of the bucket key, so deploying a change to it resets every in-flight IPv6 bucket once. `RateLimiter::client_ip()` reads `REMOTE_ADDR`, filterable through `moving_quote_client_ip` for a site behind a trusted reverse proxy (see "Behind a reverse proxy" below); every `submit` 429 also increments a counter for a fixed 24-hour window (no IP, no PII) that `StuckDeliveryNotice` surfaces once it's non-zero, so a burst of rate-limited customers is visible to the site owner instead of silent.
- **Spam bound: the customer auto-reply can relay to any address.** The customer email (see "process-lead" above) is sent to whatever address the form's `email` field holds — there's no verification that the submitter owns it — and its body echoes the submitted `name`. A submitter could use the form to relay a bounded amount of unsolicited mail to a third party's address, with their own chosen name in the body. What bounds it: the honeypot (a bot filling every field, including `website`, is turned away before anything is saved or sent), the `submit` rate limit (5 per hour per IP), and Gmail's own daily sending cap (documented in "Scaling" above). A CAPTCHA on the form is the upgrade path once that bound isn't enough for a given deployment's traffic; this demo doesn't add one.
- **Output safety.** CSV cells pass through `Admin\CsvEscaper`, which prefixes a value starting with `=`, `+`, `-`, `@`, a tab, or a carriage return with `'`, so a formula-looking name can never execute when the export opens in a spreadsheet application. The Google Sheets append writes cells in `RAW` format, so neither a phone number nor a formula-looking name is reinterpreted by the sheet's own type coercion. The team's plain-text email has no markup to break out of, but it does have lines to forge: a control character in a lead field could otherwise inject an extra "Phone:"/"Email:" line into the alert. `LeadValidator::validate_name()` (WordPress) normalizes every C0 control, DEL, and Unicode line/paragraph separator in `customer.name` to a single space before a lead is ever saved — it normalizes the name only. `move.origin` and `move.destination` need no normalization of their own: `validate_city()` only accepts a value matching one of the merchant's own configured city names, so neither field can ever carry a control character a configured city name doesn't already have. `map-lead.ts`'s `oneLine()` still runs the same normalization on every lead-derived value (name and cities alike) interpolated into the team email's body, as a second check on the n8n side, independent of what WordPress already guarantees. The email address rule on both sides (`LeadValidator::validate_email()`, `src/nodes/lead.ts`) rejects any address containing whitespace, a control character, or any of `" , ; < > ( ) [ ] : \`, which closes the one gap `FILTER_VALIDATE_EMAIL` alone leaves open — a quoted local part such as `"a,b"@example.com`, which Gmail's own `sendTo` would otherwise split into a second recipient. Every dynamic value in the customer's HTML email is escaped separately, since that email is HTML, not plain text. `LeadController` passes the raw REST body to `LeadValidator` with no `sanitize_text_field()` pass, so `validate_name()` is the real guarantee, and `parseLead()` rejects that same character set outright in `customer.name`, `move.origin`, and `move.destination`, for anything that skipped WordPress. `site_name` and `team_email` are left out of that check: `site_name` reaches only an already-`oneLine()`'d subject, and `team_email` only a `to` or `reply_to` field, never body text.
- **Data protection.** No IP address is ever stored: `RateLimiter`'s bucket key is `hash_hmac('sha256', ip, wp_salt('nonce'))`, truncated to 20 hex characters. The Postgres role for the app database (`APP_DB_USER`) can't reach the `n8n` database and vice versa (`REVOKE ALL … FROM PUBLIC`). Every long-running service's port that doesn't need to be reachable from outside Docker (MySQL, Postgres) is never published; only WordPress (`8080`) and n8n (`5678`) are, both on `127.0.0.1`. See "Token retention, precisely" below for what n8n itself keeps and for how long.
- **Single-site only.** `Install\Installer::activate()` refuses with `wp_die()` whenever `is_multisite()` is true, not only on "Network Activate": `$network_wide` is false for a per-site activation on Multisite too. The plugin was never verified on Multisite, and there every site's admin could point the webhook at an internal address and read the response back through a lead's `last_error`, an SSRF read-back.
- **Gmail is scoped to send-only.** n8n's `GmailOAuth2Api` credential (checked against 2.45.7) defaults to broad scopes (`gmail.modify`, full `mail.google.com`). Every workflow here only sends, so `cvbCredGmail0001` sets `customScopes: true` and `enabledScopes: 'https://www.googleapis.com/auth/gmail.send'`, narrowing both the consent screen and the token. The Sheets credential (`cvbCredGSheets01`) keeps n8n's default. An existing local stack must re-import and re-consent: `pnpm run setup -- --refresh cvbCredGmail0001`, then "Sign in with Google" again on that credential. Re-consenting doesn't revoke the older, broader grant; revoke it by hand at [myaccount.google.com/connections](https://myaccount.google.com/connections).
- **`WP_DEBUG_LOG` is for the local stack only.** `compose.yaml`'s `WORDPRESS_CONFIG_EXTRA` sets `define( 'WP_DEBUG_LOG', true )` (with `WP_DEBUG_DISPLAY` false, so nothing ever shows a visitor a stack trace), which writes every notice, warning, and error to `wp-content/debug.log` — the same directory a default Apache/PHP document root serves. In production, turn `WP_DEBUG_LOG` off entirely, or, if ongoing logging is still wanted, point it outside the web root instead (`define( 'WP_DEBUG_LOG', '/var/log/wordpress/debug.log' )`, a path `WP_DEBUG_LOG` accepts directly as of WordPress 5.1) — `wp-content/debug.log` at its default location is web-readable unless the web server is separately configured to deny it, and a debug log can carry a stack trace with a file path, a query, or other detail a production site shouldn't expose to an anonymous request.

### Behind a reverse proxy

`REMOTE_ADDR` is the direct TCP peer. Behind a reverse proxy that's the proxy's address, so every visitor would share one rate-limit bucket. Filter `moving_quote_client_ip` to the real client IP, but only once `REMOTE_ADDR` itself is a configured proxy address: trusting `X-Forwarded-For` or `CF-Connecting-IP` unconditionally lets any visitor send that header and pick their own bucket. The leftmost `X-Forwarded-For` hop is whatever the client sent; only the rightmost hop that isn't a trusted proxy was added by infrastructure you control. For example:

```php
/** True when IPv4 $ip falls inside CIDR block $cidr (e.g. '173.245.48.0/20'). */
function moving_quote_ip_in_cidr( string $ip, string $cidr ): bool {
    [ $subnet, $bits ] = explode( '/', $cidr );
    $ip_long           = ip2long( $ip );
    $subnet_long       = ip2long( $subnet );
    if ( false === $ip_long || false === $subnet_long ) {
        return false;
    }
    $mask = -1 << ( 32 - (int) $bits );
    return ( $ip_long & $mask ) === ( $subnet_long & $mask );
}

add_filter( 'moving_quote_client_ip', function ( string $ip ): string {
    // Cloudflare's edge ranges (narrowed from https://www.cloudflare.com/ips/; keep in sync).
    // CF-Connecting-IP is trusted only when REMOTE_ADDR is one of them: a visitor reaching
    // WordPress directly can send that header too.
    $cloudflare_ranges = [ '173.245.48.0/20', '103.21.244.0/22' ];
    $is_cloudflare      = false;
    foreach ( $cloudflare_ranges as $range ) {
        if ( moving_quote_ip_in_cidr( $ip, $range ) ) {
            $is_cloudflare = true;
            break;
        }
    }
    if ( $is_cloudflare ) {
        $forwarded = isset( $_SERVER['HTTP_CF_CONNECTING_IP'] ) ? sanitize_text_field( wp_unslash( $_SERVER['HTTP_CF_CONNECTING_IP'] ) ) : '';
        return false !== filter_var( $forwarded, FILTER_VALIDATE_IP ) ? $forwarded : $ip;
    }

    // Any other trusted proxy: walk X-Forwarded-For from the right and take the first hop that
    // isn't one of your proxies. Reading from the right ignores a visitor's forged leftmost hop.
    $trusted_proxies = [ '10.0.0.5' ]; // your own reverse proxy's address
    if ( ! in_array( $ip, $trusted_proxies, true ) ) {
        return $ip; // not behind a trusted proxy: REMOTE_ADDR is the real client
    }
    $header = isset( $_SERVER['HTTP_X_FORWARDED_FOR'] ) ? sanitize_text_field( wp_unslash( $_SERVER['HTTP_X_FORWARDED_FOR'] ) ) : '';
    $hops   = array_reverse( array_map( 'trim', explode( ',', $header ) ) );
    foreach ( $hops as $hop ) {
        if ( in_array( $hop, $trusted_proxies, true ) ) {
            continue;
        }
        return false !== filter_var( $hop, FILTER_VALIDATE_IP ) ? $hop : $ip;
    }
    return $ip;
} );
```

### Token retention, precisely

n8n stores the incoming `Authorization` header **unredacted** (checked against 2.45.6) with every run that passes the Webhook node's own `jwtAuth` check: `ExecutionPersistence.create()` builds the trigger output from the raw `req.headers`, so the token lands in `execution_data` from the start, for every outcome — accepted, duplicate, or rejected.

- **Successful runs are soft-deleted, not kept.** Both `lead-intake.json` and `process-lead.json` set `saveDataSuccessExecution: 'none'` in their own workflow settings (`error-handler` doesn't set it). Accepted, duplicate, and 401/422-rejected runs all succeed at the workflow level. With pruning on (`EXECUTIONS_DATA_PRUNE: true` in `compose.yaml`), the save hook sets `deletedAt` about one hour in the past (n8n's hard-delete buffer) while `status` stays `running`: `deleteInFlightExecution()` returns before writing a terminal status, in any response mode. The hard-delete task then purges the row and, through the FK cascade, its `execution_data`: about 15 minutes by default, longer after a restart, since each restart resets that task's timer.
- **Failed runs** (the missing-`config.json` case, not a 401/422 rejection) keep the token and the customer's name, phone, and email for the full `EXECUTIONS_DATA_MAX_AGE`, 168 hours (7 days) in this stack. `settings.saveDataErrorExecution` stays at its default on purpose: a failed run needs its data for diagnosis.
- **Manual runs** (started from n8n's own editor) are purged under `saveManualExecutions: false` — also set in both `lead-intake.json` and `process-lead.json` — without the backdate applied to automatic runs, so they're purged an hour or more later than a production run.
- **What bounds the exposure in the meantime:** the token's own 300-second lifetime (checked independently of whatever n8n stores), its `body_sha256` binding to one exact request body, and its `jti` — the lead's own `request_uuid` — which `processed_events`' primary key dedupes. A token read out of a stored execution, even before it's purged, can replay the same lead but can never create a second one. There is no execution-level redaction on the n8n 2.45 line for a `responseNode` webhook; the mitigation here is a bounded blast radius and a bounded window, not a hidden token.

`tests/stack/n8n/intake.test.ts` checks this read-only, finding an execution by its `request_uuid`, never a token, and never writes to n8n's tables: the soft-delete and the purge are n8n's own job, on its own schedule.

## Decisions

- **Testing strategy.** PHPUnit 11 covers every pure class with exact cases and no WordPress bootstrap; a stack suite built on Vitest drives the real Compose stack over HTTP and WP-CLI for everything WordPress-coupled. CI runs the stack suite as two parallel jobs, `Stack (WordPress)` and `Stack (n8n)`, each from a fresh checkout, behind one required `Stack` check. The n8n half boots the whole stack (MySQL, WordPress, WP-CLI, Postgres, n8n), and with no Google credential in CI, every case that would reach `process-lead` runs instead of skipping, asserting the hand-off reaches `Append lead row` and fails there on the missing credential — proof the chain actually executes, without touching a real Google account. WordPress's own core test suite was rejected: WordPress 7.1.4's suite still needs `yoast/phpunit-polyfills ^1.1`, which caps PHPUnit at 9, below this project's PHPUnit 11 standard. `wp-env` was rejected too — it would boot a second WordPress next to the Compose stack the README already runs. See `docs/testing.md` for the full breakdown.
- **JWT over a hand-rolled HMAC header.** n8n's Webhook node natively supports `jwtAuth` (checked against 2.45.6's own source, `Webhook/utils.ts`). Using it keeps the secret in an n8n credential rather than a workflow expression, and it rejects a missing or badly signed token before any execution starts. A hand-rolled HMAC header would need the same signing work on the WordPress side, plus a Code node on the n8n side to parse and verify it — strictly more code for the same guarantee.
- **One UUID end to end.** The browser mints `submission_id` once per page load; it becomes the leads table's `request_uuid`, the JWT's `jti`, and `processed_events`' `event_id`. One identifier threading through every layer means a retry at any point — a double submit, a cron retry, an n8n-side replay — is recognizable as "the same request" without translating between separate ID schemes.
- **Inline first attempt plus the outbox.** A lead's first delivery attempt runs synchronously, right after the insert, so a lead delivered on the first try reaches n8n within the same request-response cycle — no 60-second wait for the next cron tick. The outbox then exists for every attempt after that: it's the only path for a lead whose inline attempt failed, and it's what makes delivery eventually consistent instead of best-effort-once.
- **The cron sidecar.** WP-Cron's own request-triggered pseudo-cron only runs when a visitor loads a page, which can't be relied on for a low-traffic demo site to retry a failed delivery promptly. A dedicated sidecar running `wp cron event run --due-now` on a fixed 60-second loop makes the retry schedule actually run on schedule, standing in for the system cron a real deployment would configure instead.
- **A committed autoloader and assets.** `plugin/moving-quote/vendor/` (the Composer autoloader) and `plugin/moving-quote/assets/quote-form.js` (the esbuild bundle) are committed rather than built at deploy time, because the plugin ships as a folder a WordPress site installs directly — there's no build step on the receiving end. CI fails when either drifts from its source, so the committed copy can never go stale silently.
- **Team email in WordPress settings.** The team's notification address (`team_email`) is set once in the WordPress admin, not hardcoded in n8n's `config/config.json`, and travels inside the signed payload on every lead. A site that changes its team inbox updates one WordPress setting, with no n8n redeploy.
- **Postgres idempotency.** `processed_events`' primary key `(source, event_id)` is the one mechanism that makes `lead-intake`'s "Record request" step atomic: the insert and the duplicate check are the same statement (`INSERT … ON CONFLICT DO NOTHING RETURNING event_id`), so two concurrent deliveries of the same lead can't both read "not yet recorded" and both proceed — exactly one gets a real `event_id` back.
- **REST endpoints register with no `args` schema.** A restrictive schema would make WordPress core answer its own 400 `rest_invalid_param` before the route ever runs, preempting the plugin's documented 422 contract. Every field is validated by `LeadValidator` instead, so every rejection reason is one the API contract actually documents.
- **The `submit` rate limit counts only a lead about to be inserted.** Counting it earlier (on any POST to `/leads`) would burn through a customer's 5-per-hour budget on a typo they're correcting, or a double-tap on Submit — attempts that were never going to save anything. Counting it after the honeypot, validation, and the duplicate lookup all pass means only a genuinely new lead spends that budget.
- **Append-before-email in `process-lead`.** The sheet row writes before either notification email, so the order guarantees only one direction: no email ever goes out for a lead that isn't in the sheet. It does not guarantee the reverse — a Gmail failure after a successful append still leaves that row in the sheet with no matching email sent, until someone retries the execution. The cost, documented as a known gap above, is that a failed append itself silently skips both emails too.
- **Append or update by `request_uuid`.** Google Sheets has no transaction n8n can join, so a retry after a lost acknowledgement would add a second row with a plain `append`. `appendOrUpdate` matched on `request_uuid` makes the write repeatable: the second attempt finds the row and rewrites the same values. The key is the full UUID, not the `MQ-…` reference shown to people, because the reference is a 32-bit prefix of a UUID the visitor's browser chooses.
- **Alerts in the team's language.** `error-handler` builds its alert in a generated Code node from the same `team_locale` and the same never-throwing reader as the team email, so the team reads both in one language, and a typo in `team_locale` still sends the alert, in English with a note.
- **CSV cells guarded against formula injection, not merely escaped for CSV syntax.** `Admin\CsvEscaper` targets the specific prefix set (`=`, `+`, `-`, `@`, tab, carriage return) that makes a spreadsheet application — not just a CSV parser — read a cell as a formula, since the export's whole purpose is to be opened in one.
- **A visitor language switcher through Polylang, with the plugin independent of it.** The site is bilingual through Polylang (free, pinned at 3.9.1), the standard WordPress mechanism, rather than a custom switcher: it gives each page and menu a language, links the translations, and ships a navigation switcher block. The plugin needed two things to follow a visitor's language, and neither ties it to Polylang. First, the thank-you redirect asks for the slug's translation only when `pll_get_post()` exists. Second, a REST request has no language in its URL, so a multilingual plugin can't set one for it, and `determine_locale()` there returns the site language. The form's REST URLs therefore carry the page's own `determine_locale()`, and the routes run under `switch_to_locale()` for any installed locale: field messages, the price's separators, and the stored `locale` (and so the customer email) follow the page under any multilingual plugin that sets the language per page. Polylang (free) doesn't translate block navigation menus, so a one-filter mu-plugin, part of the demo site rather than the plugin, adds them.
- **A stuck-delivery admin notice, not a silent retry queue.** A `failed` lead, or one `pending` for over an hour, is surfaced directly on the Dashboard and the Leads page to a `manage_options` user, rather than relying on the outbox's own backoff schedule (up to 6 hours between attempts) to eventually resolve or exhaust it unnoticed. A lead the team has already closed out (`won` or `lost`) is excluded from the count: once a human has resolved the lead, its own delivery status stops being something the owner needs to act on.
